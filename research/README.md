# G2 源码与机制实验

状态：G1已通过（design/g1/g1-gate.json），开始G2定向源码与机制实验。

研究依据为design/g1/research-questions.md、alternatives-review.md的H01—H10及原始research.json要求。研究结论不得代替G3—G5的实际组件与系统验收。

## 记录与执行规则

1. 先定位维护方仓库、关联仓库与固定提交；保存来源URL、取回时间、HEAD、相关路径、许可证及所用依赖。研究克隆放在本目录repos下，实际环境/缓存放在Linux本地，不提交完整依赖或仓库副本。
2. 按问题阅读真实调用链、持久记录、进程/权限边界和失败路径；区分维护方声明、源码事实、实测和推断。README、类名或resume接口名不构成能力通过。
3. 每个实验运行前在该项目protocol中登记问题、对应性质/H假设、固定输入和可观察输出、判据来源、真实依赖与替身范围、正常/相关错误对照、命令、停止条件。探索实验回答能力边界；如果结果用于正式组件验收，须另过G3契约与用例冻结。
4. 各批次新建evidence目录，保存命令/退出码/版本/原始输出及独立目标侧观测。失败不覆盖；网络不可用、缺依赖与未运行不填PASS。候选相关机制失败可以支持拒绝候选，但不关闭系统必须性质。
5. 对每个主项目、NATS和Daytona所选历史机制，留下职责与状态归属、至少一个相关可复现实验、具体可复用模块/接口、适配缺口、不采纳设计及理由。Grok候选保持身份未知，按实际问题选择适用深度，不伪称用户原想的是某一个。
6. 汇总时比较机制族和完整交接流程，避免只比较品牌。新增来源须指向具体证据缺口。拟采用方案须有足够证据支持对应抽象和独立组件拆分，许可证与第三方使用条件已核查；其他机制作为拒绝或备选保留。

## 资源与凭据

所有操作在WSL Ubuntu /path/to/loom中进行。研究脚本只得到所需非敏感fixture；模型代理使用独立兼容性实验，不把凭据传递给克隆代码。凭据从项目外受限文件读取且不进入日志、异常、版本或任务沙箱。

本机Linux容器引擎、用户命名空间仅是可行性线索。沙箱实验必须显式核对实际身份、挂载、FD、网络、停止后的子进程写能力及资源边界；当前默认seccomp unconfined不能作为隔离证据。

## 单项目最小记录结构

- identity.json：维护方来源、固定提交、许可证、相关依赖和发现路径。
- analysis.md：问题、源码锚点、职责/状态、机制比较、适配缺口和不采纳理由。
- protocol.json或protocol.md：先行判据、输入、对照、命令和边界。
- experiment脚本及evidence批次：原始运行事实、版本与结论范围。

各角色独立编写自己的项目记录，不并发修改总manifest或task-state。根Agent收敛清单，独立角色从原目标与原始证据检查C01—C05后才进入组件实现。
