# 长任务执行指南

状态：持续任务的执行指南；系统性质尚未验证。来源为用户约束、[v5](../harness-runtime-revised-v5.md)及[调研清单](../harness-runtime-open-source-research-list.md)。用户已明确按 GOAL.md 在 WSL/Linux 中继续完整目标；实际运行状态以应用为准。

当前暂停和恢复后的收敛顺序以[2026-09-13 暂停复盘](pause-review-2026-09-13.md)为入口：成熟能力优先、小能力独验后立即装配、原 M01 为下一交付；以下阶段门槛和完整范围保持不变。文档整理不解除用户暂停。

## 1. 工作目标与资产顺序

完整交付系统及其可复现验收证据。目标、原则、抽象和判断依据决定代码方向，应作为长期资产维护。治理文档已交付，当前长期范围以 GOAL.md 为准。开发、构建和验证均使用 WSL Ubuntu 内的 /path/to/loom，产品只面向 Linux；平台及证据范围见 [Linux 执行环境](linux-environment.md)。

先把资料分成：已确认目标与原则、核心不变量、待验证工程决策、事实、假设、未知项。候选项目或样例中的名字、目录和数字不能自动成为正式接口或容量承诺。

正式目标与用户新指令优先于工作摘要。发现资料冲突时记录冲突与依据；能从原始材料解决的自行解决，决定根本目标且无法推导的事项保持未决。局部门槛未过时可并行处理不依赖它的已授权工作。

## 2. 阶段门槛

门槛是证据条件，由执行者与验收者自行检查，不要求用户逐轮批准。使用[检查表](checklists.md)记录条目、证据引用和裁定；未过项不得靠一句“风险可控”跳过。

| 阶段 | 必须产出 | 可进入下一层的条件 |
| --- | --- | --- |
| G0 目标基线 | 目标、非目标、核心场景、优先级、必须性质、范围与未知项 | 每项原始要求有去向；当前里程碑与最终系统范围分开；重要歧义未冒充结论 |
| G1 顶层抽象、论证与模拟 | 责任与状态归属、分层、契约草案、备选路线和取舍、关键正常与失败场景推演 | 影响分层和恢复边界的关键假设有支持；核心反例得到处理；可说明模型与现实的差距 |
| G2 定向调研与组件划分 | 问题—机制映射、源码依据、固定版本实验、采用与否理由、组件边界 | 候选能力在本系统条件下可检验；明确复用边界和缺口；能够准备独立验收契约 |
| G3 组件验证准备 | 性质契约、真实依赖与替身范围、可运行用例、独立预期、失败对照 | 当前未实现能力会被验证器识别为未实现或不通过；用例实际执行且判据有效 |
| G4 独立构建与验证 | 组件实现、真实执行证据、失败修复与相关回归、结构审查 | 组件契约必须项通过；重要异议有证据解决；相关证据绑定当前版本 |
| G5 组合与系统验证 | 契约衔接、真实依赖交互、端到端任务、相关故障和资源观测 | 已验组件以相同语义进入组合；系统性质有相应层级证据；无以局部通过替代整体保证 |
| G6 独立终验与交付 | 目标覆盖矩阵、独立复核和复跑、当前版本清单、限制与恢复说明 | 约定范围必须项全部通过且证据有效；没有未解决的完成阻塞 |

G1 允许为顶层判断做有明确问题、判据和退出条件的最小模拟或事实实验；其成果不自动成为生产实现。G2 的框架实验验证候选机制；G3—G4 验证本系统要复用或适配的组件契约。两类实验可复用有效证据，但结论范围不能混淆。

顶层“充分”指关键责任、边界、取舍和反例足以支持下一层，并非消除一切未知。允许延期的未知项应说明不影响当前门槛的理由、验证安排与触发条件。

发现新证据否定上层假设时，回到最早受影响阶段。修改决定后作影响分析，使相关契约、实现与证据重新同步；不在底层堆补丁维持已经失效的设计。

## 3. 调研如何收敛

先依据系统问题分配调研深度。主清单中的项目逐项留下结论；身份未定的 Grok Bot 候选按原清单处理，不能伪称已确认，也不自动要求全部深入。新增项目由明确的机制缺口、比较需要或未解决风险驱动。

克隆时记录实际仓库、提交和相关配置。每个主清单项目按原要求保留职责与状态说明、一个相关的可复现实验、模块位置以及不采纳部分和理由。实验无法运行时记录原因和缺失结论，该项仍未完成，不能以 README 摘要代替。

区分维护方声明、源码阅读、实际观测与推断。采用组件前核查相关代码和依赖的复用条件。报告回答“本系统哪项性质得到何种支持”，不能以介绍项目数量衡量完成。

当既定项目交付得到处理、关键路线已可比较、影响选择的假设有足够证据时收敛。范围外的新兴趣进入候选记录，不挤占必须项。

## 4. 构建与修复循环

每项当前工作关联目标、性质或阻塞；同时声明本轮要获得的证据和停止条件。顺序为：准备判据与用例 → 实现 → 实测 → 与判据比较 → 缩小失败 → 修复 → 相关回归。

重复失败时必须更新诊断：区分实现错误、环境错误、验证器错误或上层假设错误。根据新假设选择能区分原因的实验；不靠盲目重试或换数据碰出绿色结果。

验证器有误可以修复，但必须用独立依据说明旧判据的问题，保留旧失败与变更记录，并重新核对原始目标。实现达不到、预算不足或修复困难不是降低标准的依据。

工作单元通过后停止对该单元的无关扩展，并自动进入下一已授权且依赖满足的阶段。不得自行把工作单元或里程碑重定义为当前任务终点。新问题先分类为既有要求遗漏、当前缺陷或范围外改进；前两者按影响处理，后者不自动扩大本次验收。微小变更只维护相关资产，不为每次编辑复制整套表格。

## 5. 长任务防偏与恢复

在阶段切换、关键决策改变、任务交接、准备压缩上下文和结束一次工作时，更新同一份恢复记录。持续工作中在自然完成的工作单元后更新，不依赖记忆中的“稍后补记”。

恢复记录必须包含：当前用户目标和授权范围、当前阶段与门槛、有效约束、已验证项及证据、失败与未决假设、实际文件版本、进行中的进程或外部操作及可查询身份、下一步动作。记录仅提供索引，正式契约与原始证据仍是依据。

恢复后先核对记录、源材料、实际文件和未决执行结果。失去回执的操作先查询，不能因摘要里没有结果就重复执行。核实变化是否使证据失效，再继续工作。

并行子任务必须交付：关联目标、范围、约束、预期产物、验收方式和未决事项。根 Agent 对目标覆盖、组件集成与最终结论负责，不能因子 Agent 报告“完成”就直接勾选。

出现时间、预算或环境限制时保存可接续状态，并继续可独立推进的工作。确实无法继续时如实报告未完成范围和所需条件；记录阻塞不代表任务完成。

## 6. 自主推进的边界

已授权范围内的例行选择、修复和验证由 Agent 完成。流程不会额外增加用户审批。若改变根本目标或必须项才能继续，不能默默降低要求；无既有授权时保留阻塞，所需澄清限定到不可推导的事项。

先完成独立验收再报告完成。目标运行时，阶段通过后持续推进下一已授权阶段；只有当前授权任务全部验收完成，或确实没有可继续的已授权工作且已保存接续状态，才结束推进。系统总目标、阶段目标和单次环境调整分别报告，阶段通过不能替代整个项目完成。尊重用户显式暂停；用户明确继续时，在最新目标范围内接续，不受历史阶段说明限制。
