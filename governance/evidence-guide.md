# 独立证据与验收指南

## 1. 独立性的可检查定义

核心性质的验收证据必须同时满足下列要求。其他 Agent 的赞同、实现者的信心或更多同源日志都不能替代这些条件。

| 要求 | 验收者实际检查什么 |
| --- | --- |
| 判据独立 | 预期来自原始目标、契约、推导、外部事实或经论证的参考结果；不调用被测实现生成自身预期 |
| 直接观测 | 读取真实产物、受控实验结果和必要原始记录；对系统性质使用具有相应观测权限的执行器、OS 或依赖侧观测 |
| 可反驳 | 关键验证能拒绝一种相关的已知错误、缺失产物、违反不变量的样本或受控故障；空跑、恒真断言和吞错不能通过 |
| 范围匹配 | 证据中的环境、输入、依赖、故障与负载，支持所宣称的结论；模拟假设及替身局限明确 |
| 版本可追溯 | 能重建被验实现、测试、数据、配置及相关依赖；证据与当前交付对象一致 |
| 裁定可复核 | 验收者能从契约和原始证据重做判断，直接复查或复跑关键检查，保留自己的结论与异议 |

“可反驳”按风险选择少量有代表性的负对照，不要求给所有代码做变异测试，也不要求第二套完整实现。结构性质可以用依赖检查、实现审查和替换实验；运行性质需要相应运行观测。

## 2. 证据类型与允许结论

| 类型 | 可以支持 | 不能据此直接宣称 |
| --- | --- | --- |
| DECLARED 外部声明 | 候选项目宣称什么、值得验证什么 | 在本系统中已满足 |
| ANALYZED 源码或结构论证 | 指定版本存在某机制、责任边界有何依据 | 运行、权限、恢复或容量已经成立 |
| MODELED 模型或模拟 | 明确假设下的状态、反例与设计一致性 | 真实沙箱、网络、进程或存储已兑现假设 |
| COMPONENT 独立实测 | 指定组件契约在测试条件下成立 | 组合后或系统整体成立 |
| INTEGRATION 组合实测 | 真实组件之间的相关交互成立 | 未测试的端到端场景、规模或故障成立 |
| SYSTEM 系统实测 | 固定范围内的实际产物与整体性质成立 | 所有输入、任意故障、无限负载均成立 |

这些是证据适用范围，不是自动继承的等级。真实模型运行一次也不能弥补缺失的权限验证；结构论证不能由无关的端到端演示取代。每项性质注明所需类型，可组合使用。

## 3. 验收契约先于对应实现

每项必须性质采用[性质卡](templates.md)，至少填写：来源、约束内容、适用范围、独立预期、观测方法、通过标准、正常/边界/相关失败场景、负对照、所需真实依赖、证据位置和责任人。开始实现前保存契约基线与可执行用例版本。

仅当有原始目标或外部事实等独立依据时，才能修订判据。记录原值、新值、原因、目标影响和重验范围；不得覆盖旧失败。用例变化需要审查是在纠错、补充覆盖，还是实际削弱要求。

正式性质的数值阈值、恢复边界、威胁范围及统计评估方案，必须在对应生产实现与正式验收前确定。尚未确定时保持待定义。v5 未冻结的 SLA、固定 UID、容量等不得擅自当成用户承诺。

允许在顶层论证或候选调研中进行探索性测量：先定研究问题、观测方法、范围和停止条件，用来估算能力、成本或选择合理指标。探索结果不计作性质 PASS；正式标准仍须有目标依据，不能把测得结果直接设为及格线。确定基线后使用新的正式批次验证；探索数据作为选型依据的角色应显式记录。

随机模型或并发实验保存预定的样本、预算、关键版本、种子（适用时）、全部运行与失败分布。采用与性质相称的重复次数和统计说明；单次成功只支持该次结果，不能宣称普遍可靠或优于另一策略。

## 4. 每个验收批次的证据包

保留以下信息，可集中在一个清单中，不要求建立专用平台：

- 批次 ID、性质及契约版本、证据类型、验收范围。
- 被验实现版本；有未提交修改时附可重建补丁或源码快照。只有文件哈希不足以重建内容。
- 验证脚本和数据版本、相关依赖版本、关键环境与配置。秘密值不写入报告，记录必要配置身份。
- 完整命令或操作步骤、工作位置、开始结束时间、实际执行身份、随机条件（适用时）。
- 实际执行的用例、跳过或未运行原因、退出状态、关键断言和负对照结果。
- 原始产物、日志及其引用；按需保留内容摘要用于核对一致性。摘要文本不替代原始来源。
- 按判据作出的逐项裁定、失败和限制、验收者的直接复查或复跑记录。

原始结果按批次保留，不用最新一次运行覆盖失败。脱敏和裁剪须标明，保留获授权的原始来源或说明无法保留导致的验证限制。

## 5. 状态与证据失效

| 状态 | 含义 | 可计入必须项完成 |
| --- | --- | --- |
| UNVERIFIED 未验证 | 未定义完、未运行或缺证据 | 否 |
| PASS 通过 | 声明范围内满足预定判据，证据有效 | 是，仅限该范围 |
| FAIL 失败 | 直接观测违反判据 | 否 |
| BLOCKED 阻塞 | 当前缺条件，无法完成验证 | 否 |
| INVALIDATED 已失效 | 相关对象或条件变化，旧证据不足以支持当前结论 | 否 |
| N/A 不适用 | 原始范围明确不包含此项，有范围依据 | 不作为通过；不能用于豁免必须项 |

不设置可替代完成的“有条件通过”。条件应预先写入性质范围；实验后缩小范围得到的 PASS 只覆盖缩小部分，原目标的缺口仍未完成。

实现、契约、用例、数据或相关依赖改变后先分析影响：受影响证据转为 INVALIDATED，修复并重验；未受影响的证据可保留，记录简短理由。最终版本与被验快照不一致时必须有可复核的覆盖说明，不能挪用旧绿色结果。

## 6. 独立验收者的工作方式

1. 先读目标、性质卡、原始范围和当前版本，再读实现者报告。独立列出必须检查项，检查目标是否有遗漏。
2. 检查证据的来源、类型、版本、真实依赖和失败记录；检查验证器本身能否拒绝相关错误。
3. 直接打开关键产物与原始记录。核心系统性质逐项复查；每个不同验证机制至少选择有代表性的检查独立复跑，高风险性质补查相关失败场景。其余复用证据须说明选择依据。
4. 复跑使用独立批次和输出位置，按锁定契约执行。验收期间不悄悄修改被验实现、预期或阈值；发现问题交回修复，再验新版本。
5. 报告逐项裁定、证据引用、异议和遗漏，不以投入时间、报告质量或多数 Agent 意见决定通过。

具备多 Agent 或外部验收器时，使用独立验收角色；具体分工和已完成审查记录在对应阶段证据中。角色分离增强检查，但若仍共享同一可写环境，它不是权限或防篡改隔离。

独立证据是普遍必须项，第二个人或 Agent 本身不是证据。仅有单 Agent 时，从锁定契约独立复跑、直接读取产物并记录原始结果，明确角色未分离及其局限，不虚构“他人已验收”。如果既定契约把角色分离列为必须项，缺少该角色仍不能完成；不得将实际可用能力宣称为不可用来逃避审查。

## 7. 常见伪证据与纠正

| 看似通过 | 应作出的判断与补充 |
| --- | --- |
| 单元测试全部绿色，但运行了零项或关键项全跳过 | 未验证；检查发现列表、实际运行项、断言和失败传播 |
| 测试复制实现公式，或把当前输出直接保存成预期 | 判据可能同源；从契约推导、可信样本或独立方法得到预期 |
| mock 返回成功，宣称真实写入、恢复或权限成立 | 只支持替身内逻辑；在受控真实依赖中验证相关性质 |
| Agent 声称报告正确，或退出码为 0 | 读取真实报告，按独立数据和判据核算 |
| Runtime 记录“沙箱已释放”“身份受限” | 需要具备相应权限的外部观测核对资源、身份及禁止操作 |
| 正常退出后可重启，宣称崩溃无损恢复 | 故障范围不匹配；检查承诺边界附近的受控中断和副作用核对 |
| 固定演示通过，宣称可替换 Harness 或通用计算 | 需要另一外部策略或独立输入检查对应性质，避免写死答案 |
| 第二个 Agent 同意报告 | 尚无独立验收；要求其读契约和原始证据并直接复核 |

## 8. 后续执行门禁的要求与边界

实现验收机制时，应把“Agent 提交完成声明”与“验证器裁定通过”分开：声明不能直接修改验收结果。至少自动检查必须项覆盖、证据存在、实际执行情况、版本一致性和验收状态；核心产物由验证器直接检查。

若要防止执行者改写判据和证据，需让基线用例、验收凭据和原始输出由独立权限域管理，并校验产物来源。哈希只能核对内容一致性；执行者可同时改文件和哈希时，哈希不是防篡改保证。是否已实现这种机制，须以当前阶段的实现与运行证据为准。

这些完成状态属于开发任务验收，不是要求在 Runtime 中新增通用 done/fail 业务协议；保持 v5 中策略定义和底座责任的边界。
