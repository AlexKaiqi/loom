# G0：系统目标与范围基线

版本：G0-draft-1；2026-09-13。状态：待原始要求覆盖与独立审查，不代表系统性质通过。权威来源为 v5、用户启动 GOAL 的要求、WSL/Linux 更正和治理约束。

## 系统目的与可观察价值

系统为长程模型任务提供中立且可恢复的运行底座。Harness 是外部推进定义，负责上下文投影、模型交互和继续策略；Runtime 承担四项底座契约的实际执行与持久交接。需要证明策略演进不在既有契约范围内侵入 Runtime，而非仅在命名上拆成两个目录。

| 目标 | 必须支持的结论 | 对应性质 |
| --- | --- | --- |
| O01 策略与运行责任分离 | 至少通过公开契约替换外部策略，并检查运行职责和权威记录没有重复或泄漏 | P01、P12、P13 |
| O02 长程等待可释放任务计算资源 | 进入等待或非执行期后，无任务专属 Agent 进程、长连接和沙箱；持久工作面及责任可保留 | P06、P07、P10 |
| O03 已确认状态和受理责任可靠接续 | 在明确恢复边界与故障范围内，无已确认状态丢失、无受理责任静默消失；未知副作用先核对 | P04、P07、P09、P10、P11 |
| O04 隔离与破坏范围可控 | 双域权限、执行身份、写入协调和外部副作用边界由实际运行机制落实 | P02、P03、P05、P08、P11 |
| O05 多 Surface 与多策略价值 | 普通外部代码定义等待及传递，条件提前发生不漏处理，策略共存和对比不共享破坏范围 | P01、P03、P10、P14 |
| O06 规模可测且不牺牲确定性 | 分别观测等待驻留、唤起和活跃吞吐；规模结论限定实际环境与负载，不用单任务演示外推 | P06、P15 |

## 保留的原则及优先关系

v5 §2 的三条原则完整保留：顺应模型训练先验；优先复用成熟工业基建；确定性与可逆性高于极致性能。普通代码、文件和 Shell 语义优先，避免新增面向模型的私有 DSL、复杂业务 Schema 或专属内容操作协议。

先兑现职责、权限、状态和恢复的正确性，再量化效率和规模；后者仍是最终范围的必须工作，不因排序靠后成为可选项。选型须能说明相对于已有机制的必要性。文档中的 Git、NATS、Session 产品、容器、微虚拟机、CLI、路径和数值均需按原文区分候选与要求。

工程执行遵守先性质/用例后开发、组件独立验证后组合、分层、变化隔离与复杂度控制。目标、假设、判断、取舍与证据是长期交付资产，不能只留下代码。

## 范围与非目标

| 范围 | 必须交付 | 不能据此越界推断 |
| --- | --- | --- |
| M 最简闭环 | 一个 Surface、一个 Workspace 的最简 Harness；真实双 Shell、文件投影、事件往返、保存/停止/接续及相关权限边界 | M 完成不等于多 Surface、任意故障或规模成立 |
| X 后续价值验证 | 代码定义多 Surface 等待/传递、条件竞态、共存策略与隔离对比、真实负载测量 | X 是本次完整 GOAL 的范围；不因 v5 将其安排在后面就省略 |
| 工程交付 | 原始要求覆盖、设计与判断、调研实证、独立组件、系统实现、验证设施、原始证据及运行恢复说明 | 治理表格写完不等于系统可用 |
| 平台 | 2026-09-14 修订：开发验证在 Unix 主机（macOS/Linux）执行，容器执行使用 Linux 容器运行时；此前 WSL Ubuntu 原生 ext4 证据保留其原环境范围 | 任一宿主的内核/容器/资源结果不能自动代替其他平台条件复验 |

不自建一套通用 Agent 框架、任务图 DSL、Surface CRUD 平台、竞争性的局部事实系统或底层文件消息服务；不要求四项契约独立部署为四个服务。不预设统一业务 done/fail、父子任务范式、全局总序、每步 Git 提交、固定 UID/FD、毫秒 SLA 或特定商业产品能力。

正式验收设施只解决本项目的证据收集与裁定，不把开发任务完成状态变成 Runtime 业务协议。

核心性质 P01—P15 的定义、独立观测与不足以证明的情形见 [性质验收映射](../governance/runtime-acceptance-map.md)。这些是判据草案，正式边界及数值仍须在对应开发前冻结。

## 原始要求的覆盖与处置

v5 提取分为 requirements/v5-a.json（§1—4、§5.1—5.2）与 requirements/v5-b.json（§5.3—7）。每项保留原文连续摘录、来源章节、类别、关联性质、里程碑、独立验收草案和未决项。用户补充约束另在 requirements/user-and-process.json；调研主清单、专项及交付约束在 requirements/research.json。汇总矩阵生成后由独立角色对照原文审阅，不能只检查字段齐全。

类别决定后续处置方式：goal/principle/invariant/contract 为相应目标或行为的必须要求；definition 用于统一抽象与责任语义；non_goal 为不得违反的范围约束；decision 要形成有依据的采用、替换或否决记录，不强制采用某个候选产品。候选方案附带的正确性保障若被核心性质要求，仍不可豁免。

当前所有系统性质为 UNVERIFIED。G0 通过只表示原始目标、范围、判据草案及未知项得到一致表达，不能把 G0 文档审查状态写成系统 PASS。

## 未知项与进入下一层的条件

见 unknowns.md。产品、工具和环境未知通常属于后续设计/调研工作，而非要求用户补充；每项指定最晚闭合阶段和证据类型。涉及正式故障承诺、威胁范围、恢复保留与容量阈值的未知，在对应生产实现前闭合，不从既有输出反推标准。

G0 的进入 G1 条件是：A01—A04 逐项有原始来源和审查依据；所有原始要求有去向；M/X 没有缩减；不存在会改变根本目标但被任意假设填补的事项。G1 首先论证策略/机制边界、权威事实、恢复交接、权限与等待模型，不提前选择底层产品。
