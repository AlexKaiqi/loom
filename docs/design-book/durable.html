04. 持久执行：恢复、等待与内容

4.1 工作如何跨越中断

持久执行（Durable）使工作不依赖某个进程始终存活。Runtime 保存继续工作所需的状态、内容和操作记录：已确认的结果可以复用，未完成的步骤可以接续，结果未知的操作须先核对。等待条件也被保存，满足后由 Runtime 安排继续。

Harness 决定业务上如何继续，Runtime 保证依据已保存的状态恢复这段逻辑。恢复范围限于约定的持久状态和受管调用，不包括任意进程栈、Shell 内存或尚未完成的模型生成；能恢复也不保证任务最终成功。

一次 Harness 调用以稳定的 run_id 关联原启动 Operation、所属 Work、父调用和继续状态。同一 Work 可以运行多份 Harness；生成并启动另一份 Harness 也使用这套记录，不另建一套调度状态。代码、入口、依赖、SDK、状态格式、初始输入及实际执行绑定在受理时固定，恢复时按原绑定重新装载。调用可以跨越进程和环境分配的更换，不能把进程 PID 或当前源码目录当作调用身份。

4.2 作者怎样表达可恢复程序

入口 作者负责 运行绑定负责
受管顺序代码 用所选 SDK 编写控制流程；可变文件读取、模型调用和外部操作均经过可记录结果的受管调用。 保存调用结果、等待和执行历史，重建控制位置并安排继续。
显式状态驱动 定义可保存的状态格式和一次推进函数，返回新状态、下一操作或等待条件。 同时确认新状态和后续待办，再按记录调用推进函数；继续依据不能只存在于内存或闭包中。

两种方式遵守相同的工作契约，但使用不同的编程接口。采用重放 SDK 时，控制位置由引擎恢复，不再由 Harness 维护另一套推进游标；采用显式状态时，继续所需的信息必须写入持久状态。具体接入见持久执行的实现。

动态生成的 Harness 同样可使用受管顺序代码。 执行绑定须支持按固定代码内容装载、隔离执行和恢复；不能因某个引擎的代码部署方式，把这一作者入口改成只能手写状态机。普通 async、直接网络请求和任意可变文件读取本身不具有持久语义；非确定结果须经 SDK 保存，子 Harness 的启动与等待也须经受管入口。运行时生成代码的具体环境与启动契约见第 7 章。

4.3 中断后的动作

已确认的边界 恢复行为
输入已受理，尚未执行 自动安排该输入；不依赖后来碰巧又来一条消息。
模型结果已保存，工具尚未开始 使用原模型结果与工具清单，按原操作身份续办。
部分并发项已完成 复用已完成项；其余项分别继续或核对，不重跑整个批次。
子 Harness 已受理，启动回执丢失 按原启动身份取得原 run_id 和回执；不创建第二个子调用。当前候选代码已改变，也不替换原绑定。
结果与产物已保存，返回回执前退出 取得原收据及内容，不再次执行命令。
可能已经派发，原结果未知 查询原目的地；只有明确可重复、原生幂等或获准新尝试时才派发。
等待已登记 从已记录输入、结果和计划恢复；条件已满足则推进，否则继续等待。
代码不兼容、内容缺失或权限撤销 明确阻塞原因与修复入口，不清空原任务或伪造成功。

恢复时重新进入一个操作，首先要查找原记录；这不等于再次执行。若策略允许重新调用模型，新尝试（attempt）单独记录用量，且只选择一个结果驱动后续步骤。外部写入可能已经成功时，执行引擎的重试不能直接触发重发。

4.4 结果等待、时间与取消

作者动作 持久契约
operation.result(id) 等待原操作的已确认结果；不创建第二个操作。等待超时携带原 id，不把操作改成未执行。
harness.result({run_id}) 等待原调用的终态和已保存结果，同时返回责任已结清或已确认转交的状态；等待位置与责任持久保存。继续所需内容固定后，纯等待期间释放该调用专属进程、模型连接和执行环境；不要求父调用保持在线，也不终止仍在推进的子调用。
inputs.next(filter) 先检查已受理的匹配输入，再登记等待；检查与登记之间到达的输入也必须触发继续。
受管 sleep 第一次确认时固定到期时间；重启不重新计时。到期后由共享调度设施安排继续。
timer.put/update/cancel 稳定计划 id、版本、绝对到期时间和载荷；重复登记不改期，修改须检查原版本。
operation.cancel(id) 记录取消请求；实际停止、已经发生的结果和未知费用继续独立核对。
harness.cancel({run_id, scope}) 明确取消本调用（self）或同 Work 调用树（tree），经授权后记录停止新意图的请求；已派发操作与迟到结果继续核对，独立子 Work 不因调用树取消而级联关闭。

周期任务默认按 origin + n × every 计算到期时间。恢复后按配置上限补交停机期间的到期输入；需要合并多期时须显式配置。计划取消与本期输入受理按同一提交顺序判断：已经受理的输入仍须处理。宿主停机时不能执行，恢复后记录原到期、实际受理和处理时间。

等待答复与获得批准分开。 拒绝也是答复，应结束等待；随后 Harness 根据原请求、来源、内容版本和答案作决定。对 v7 的批准不授予 v8 的发送权。

allSettled 保留各项成功／失败；race 返回赢家和等待超时都不自动取消其他操作或子 Harness。父调用结清前，须等待其子调用及未结操作完成、完成取消核对，或由有权的承接者确认责任转交。父进程退出、模型回答结束和资源释放不能替代这一确认。

业务结果已保存与执行责任已结清分别表达。未结操作可由 Runtime 持久接管或确认转交后让 Harness 返回业务结果，但回执必须保留承接记录与未结操作；不能把已接管的未知效果标成成功、已停止或责任已结清。

Work 输入仍由输入契约控制：子调用默认只取得固定的调用输入，不自动消费 Work 输入队列。需要移交当前输入时，通过inputs.transfer 以原 processing_ref 确认承接者并撤销旧处置权；仅复制输入正文不转移处置责任。

4.5 内容与历史读取

入口 输入与返回 确认边界
content.read(ref) 确定引用及可选范围 → 字节、来源、范围。 不读取同名对象的“最新版本”代替原引用。
content.save / capture 字节或稳定来源 → 内容引用。 已校验、耐久且受保留；不表示共享项目已更新。
content.apply 新内容 + 目标 + 预期基线 → 整合回执。 目标基线相符才更新；冲突不覆盖。
history.open/read/search Work、授权范围、固定游标 → 记录、覆盖范围、分页游标。 读取不执行旧工具、不消费输入；无命中不证明不存在。
view.open 必需记录范围 → 固定只读文件／SQLite 视图。 未覆盖所需范围返回 not_ready／history_gap；视图不是新权威。

保存顺序为 保存必要字节 → 防止提前清理 → 提交结果或状态引用 → 返回成功回执。文件可见、版本固定、字节已持久保存和共享项目已更新，须分别确认。只读查询缓存可重建；原文与必要操作收据不可当缓存清理。

若原步骤读取的是 Surface v12，恢复该步骤仍使用 v12；后续新步骤才可读取 v13。读取当前事实视图同样属于新的观察，须保存结果才能在恢复时复用。

4.6 生命周期与保留

动作 改变什么 保留什么
Archive 后续模型上下文选择。 原始记录、输入处置、等待、操作及其内容。
运行历史滚动 把继续状态交给新的引擎运行实例，限制单次执行的历史长度。 Work、所有未结 Harness 调用及原代码绑定、回执、未处理输入、计划、未结操作和必要状态。
Work 关闭 进入 closing 后，所有所属 Harness 调用停止产生新业务意图，结清调用、输入、计划和操作责任后形成最终处置。 历史、原回执、未知操作的核对与迟到结果；耗时清理须已交给独立的持久任务。
Fork 从确定基线创建新 Work。 原工作及原责任不改变；新 Work 不继承执行权、秘密或未知效果重放权。

未结调用需要的代码内容、依赖、SDK、状态格式和继续记录受保留保护。修改工作区中的候选源码或选择新版本，只影响新调用；不能覆盖原调用的恢复版本。原依赖缺失、原隔离环境不可用或权限撤销时明确阻塞，不静默改用最新代码或放宽环境。

目录导出保存资料及导出格式声明支持的继续状态；完整备份还须包含实际执行引擎的状态。不能仅复制 .loom/durable.json 就创建第二个活跃执行者。历史保留范围、引擎清理期限和内容 GC 必须协调；永久可读只在相应部署验证后声明。
