07. Harness：推进逻辑与组合

Harness 回答“怎样把问题持续推进到有依据的结果”。它组织每一步所需的信息、模型判断、实际行动和结果检查，并根据反馈决定下一步。控制流程可以由代码预先规定，也可以让模型在获准工具和停止条件内选择行动。

Runtime 在持续接管工作的同时，可以运行不同 Harness。A 中的模型可以编写 B，A 通过受管入口启动 B 并等待结果；B 也可以调用 C。每次调用固定实际代码和执行绑定，等待或进程退出不丢失调用责任。完整轨迹见生成与组合示例。

7.1 定义推进逻辑

职责 最小定义
目标与输入 要解决什么问题，接收哪些输入，何时把新信息纳入当前工作，以及如何记录处理结果。
信息与判断 为每一步选择什么信息、模型和工具，怎样检查模型的回答，以及哪些结论需要外部证据验证。
推进 如何衔接行动与检查，哪些步骤可以并行，失败后重试、改换方案还是停止，何时等待用户或外部条件。
上下文容量 信息持续增长时，选择摘要、检索、归档或有界保留。Runtime 提供容量和格式检查，Harness 决定保留哪些信息。
进度与完成条件 明确什么结果算完成，哪些业务状态是继续工作的依据；通过受管顺序代码或显式状态驱动交给 Runtime 保存和恢复。

以调研为例，Harness 可以先让模型列出疑点，再并行收集证据、检查相互冲突的结论，最后决定补查或交付。Runtime 保存各次调用和采集结果；中断后复用已完成的部分。决定“还缺什么证据”属于推进逻辑，保证“已有证据不会因中断而丢失”属于运行机制。

作者提交固定代码描述，声明可运行材料、允许的入口、SDK 与依赖要求，以及受管顺序或显式状态作者形式；Runtime 据此形成获准的实际执行绑定。代码可以来自运行期间生成的文件。描述格式、作者入口与公开配置由第 8 章定义；输入交付、操作核对、调度和权限检查由 Runtime 提供。

7.2 组合与替换策略

能力 可替换什么 状态／权限边界
上下文 会话＋archive、Surface、检索或批量片段。 同一次模型请求的内容选择由一个明确组件负责；多个裁剪策略必须协调，避免互相覆盖选择。
推进驱动 ReAct、固定评审、验证分支、事件响应。 保存推进所需的业务状态，通过 Runtime 调用模型和执行环境。
工具 schema、参数校验、结果呈现与操作语义。 不自行扩大授权或伪造 Runtime 结果。
模型路由 模型选择和请求参数策略。 提交前可以调整；Runtime 受理后保存原请求和原服务绑定，恢复时不重新选择。
观察 UI、统计、诊断。 读取已确认结果。若观察组件不承担验收责任，它的故障不应阻止业务结果提交。

扩展点（Hook）须明确调用顺序和可修改的内容。提交前的请求可以依序调整；授权与完整性检查一旦拒绝，后续普通扩展不能覆盖拒绝结果。结果展示可以加工，但须保留原始返回。注册名称冲突时拒绝或要求显式替换。

卸载组件时，先停止接收新调用，再完成或转交已有调用，最后移除注册并清理临时资源。Work 的状态和未完成操作仍由 Runtime 保留。模型与工具的实际效果通过 Runtime 的受管入口；组件自己的内存状态、会话文件或恢复循环不能成为另一份推进权威。Pi、DSH、Cordis 等零件如何适配见组件复用。

7.3 Harness 运行环境

Harness 运行环境由 Runtime 按宿主已授权的 Profile 提供，声明允许的作者形式、运行时、SDK、隔离与恢复能力。作者选择相容的逻辑环境，Runtime 固定实际绑定后承担执行责任。参考运行环境、代码装载、SDK 通道与进程管理见Harness 执行管理。

Runtime 提供确定行为
代码与依赖装载校验代码描述和入口；装载绑定的源码、SDK、依赖及运行时。缺失内容或不相容入口明确拒绝或阻塞，不在恢复时读取最新文件、下载最新依赖。
调用范围内的 SDK提供模型、内容、工具、事件、输入、等待和 Harness 调用入口。身份来自受信连接，调用只可使用获准能力；供应商凭据及引擎管理连接由可信侧持有。
工作内容与临时空间按授权提供 Work 文件和 Userspace 内容。候选代码可通过工具编辑；正在执行的代码使用固定快照。临时文件和内存不能成为唯一继续依据。
运行、释放与重建按绑定启动执行、记录继续位置和等待。纯等待允许释放本次调用的专属进程与临时环境；唤醒后按原绑定重建，通过记录复用已确认结果。
限额与隔离执行 CPU、内存、并发、调用深度及业务预算限制。子调用可收窄范围，不因父子关系扩大 Work 授权；代码不能取得宿主管理能力或其他 Work 私有状态。

Harness 程序通过 SDK 使用运行能力；模型看到的工具集合由 Harness 决定。首个 Basic 默认提供 Bash 与精确编辑，并保留其上下文整理入口。只向模型暴露 Bash 是另一种 Harness 工具策略，可在获准的 Work 工具环境中提供受限 loom CLI 来完成相应操作。该 CLI 将启动、查询或取消请求交给同一 Runtime 契约；它取得的是当前范围的操作入口，不是管理连接。CLI、SDK 和模型工具不能各自另实现状态或授权。

编写与构建候选代码的 Bash 属于受控工具执行，和执行 Harness 程序的恢复绑定分别声明。普通 Shell 的栈、后台进程和局部变量不因调用 CLI 而成为持久状态。用户项目中的命令环境不接收 Harness SDK 通道；两种环境可以复用环境分配、限额和内容交付设施，但须分别核验入口与资源范围。命令契约见第 6 章。

7.4 生成与调用 Harness

harness.start 是受管 Operation。它接收固定 code_ref、允许的 entry、固定 input_ref、逻辑 environment 及可选的收窄限额；外部调用提供 request_key，受管 SDK 可由执行记录保存稳定键。code_ref 引用完整代码描述，SDK、依赖和状态格式不由每次调用随意覆盖。载荷见Harness 接口类型。

入口确认内容关键失败与继续
harness.start核验代码、入口与授权，固定实际环境及恢复绑定，保留必要内容并登记调用责任，返回 operation_id 与稳定 run_id。受理不等于已开始或业务成功。同键同请求返回原调用；同键改变代码、输入或入口冲突。代码或能力不适用时明确拒绝；已受理后的暂时故障保留原调用并报告阻塞。
harness.result({run_id})等待原调用的已确认业务结果，返回结果引用、失败或取消记录。提前完成的结果同样可匹配后来的等待。超时或取消等待不取消被等待调用。结果已产生而操作或清理尚未结清时，返回保留或转交责任的依据，不将其伪装成全部完成。
harness.inspect({run_id})读取原绑定、推进、等待、阻塞原因、取消状态、结果与未结责任。查询不重新启用代码或改变环境状态；无权限、不可用及未知分别报告。
harness.cancel按稳定键请求停止原调用；显式选择 self 或同 Work 后代 tree 范围。取消受理、停止新推进、实际外部操作停止分别确认。独立子 Work 不因 tree 自动取消；未知或迟到结果仍需核对。

run_id 标识同一 Work 内一次调用的代码、输入、继续状态、子调用和所属操作；它可以关联启动 Operation，不建立第二套执行引擎。A 调用 B 和 B 调用 C 使用同一 Work 的授权及总预算，分别登记来源与责任。仅当另一项工作需要独立身份、长期输入或关闭责任时，使用获准的创建 Work 操作。

调用限额的计数

max_parallel_calls 限制该调用及其后代同时未结束的调用总数，包含该调用自身；Work 的总上限覆盖所有所属调用，子调用还同时受每个祖先的范围上限约束。accepted、running、waiting、blocked 和 unknown 均占逻辑调用名额。保存业务结果并结清或确认转交责任后，调用才释放该名额；已转交的原操作仍按自身资源与费用契约核对。纯等待释放的是专属进程和闲置环境，不释放逻辑调用名额。物理执行并发由环境 Profile 另行限制。

初始 Harness 深度为 0，每次子调用加 1；max_depth 是从 Work 初始调用计数的最大绝对深度，不是给每个子调用重新分配的层数。两个限额均为正整数，省略时沿用父范围，声明时只能收窄。启动超出任一上限返回 call_limit_exceeded，不先受理再无限排队；Harness 据此减少批量或调整计划。例如 A 等待 B、B 同时运行 5 个 C 时，共占 7 个 Work 调用名额，最大深度为 2。

B 默认接收调用参数，不自动领取 A 的 Work 邮箱。Work 输入的领取与处置由明确所有者负责；把已领取输入交给 B 时，持久转交原 processing_ref，防止重复处置。A 结束前须等待所属子调用结清，或完成取消核对或责任转交；Runtime 接管的未结事项可以继续核对，不因 A 进程退出消失。调用结果、等待和剩余责任的恢复见第 4 章。

7.5 工作材料与公开配置

作者使用代码、固定输入和获准工作材料，按策略选择 Surface、归档或其他内容组织方式；Work 配置声明初始入口及逻辑资源。Surface 不要求保存完整历史，独立 Userspace 不随 Work 关闭而删除。公开 work.toml 见第 8 章。

源码、依赖、输入和图定义沿用内容与版本契约，正在执行的调用使用固定材料。Runtime 私有目录、Worker、队列和存储布局由实现管理，参考布局见Harness 执行管理；作者不依靠读取这些私有文件推进或恢复工作。

7.6 代码版本与信任

Harness 代码可通过 Git 分支和 worktree 维护，也可以在运行中由模型生成。候选内容通过入口、SDK、依赖、能力和限额检查后，保存为不可变代码描述，再用于新调用。保存文件不替换正在执行的版本；A1 启动 B1 后，即使候选文件变成 B2，恢复仍使用 B1。原代码、依赖、SDK 与继续状态所需内容须保留到责任结清。

受管顺序代码与显式状态推进均是作者入口。动态顺序代码需要可装载固定内容、按 SDK 记录调用、释放等待资源并恢复原调用的实际绑定；普通 async 不能代替该保证。显式状态形式需要同时确认新状态与操作、等待或结果。不同形式都遵守相同操作契约；引擎方案及待验证接合点见持久执行的实现。

模型生成的 Harness 在已经授权并验证能力的隔离 Profile 内可直接启动。将它提升到共享 Worker 作为受信宿主代码运行，或扩大资源与权限时，才检查相应批准。代码格式检查不保证解题正确，结果仍由 Harness 的业务验收负责。原运行升级须明确状态迁移与未结操作处理；不能靠修改最新文件实现热替换。

7.7 图结构与展示

Harness 可以定义自己的图映射和结构规则：哪些内容作为节点，什么关系作为边，怎样的一组节点和关系构成某种结构，以及怎样命名和描述。结构定义随 Harness 材料保存，不要求展示名称预先成为 Runtime 内置对象。

Runtime 提供获准的记录和内容，Harness 或语义转换器生成可追溯的图快照，graph 负责唯一的通用展示。图中区分运行事实、推导与未知；坐标、布局、名称和折叠不授予权限，也不决定调用完成或如何恢复。完整快照、定义版本、来源范围及更新契约见第 10 章。
