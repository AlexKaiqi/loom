07. Harness 定义与组合

7.1 作者至少定义什么

职责 最小定义
输入 接收哪些输入、何时采用、如何处置。可以是一次调用，也可以长期消费输入。
模型请求 如何形成 messages、选择模型和工具；不增长的请求不要求 archive。
推进 继续、并行、等待、失败处理和结束条件。只有 Basic 采用固定的 tool-call 循环。
上下文容量 对增长输入选择 archive、摘要、检索或有界保留；Runtime 只提供容量和合法性反馈。
恢复入口 选择受管顺序代码或显式状态驱动，保存足以恢复的必要依据。

输入可靠性、原操作核对、共享调度和权限机制不由每份 Harness 重写。发布材料固定实际入口、代码、状态 schema、能力及依赖；它们是运行材料，不是每个作者都要重新编写的基础设施。

7.2 独立变化与组合契约

能力 可替换什么 状态／权限边界
上下文 会话＋archive、Surface、检索或批量片段。 同一次投影有一个明确的选择所有者，不能有两个未协调的裁剪游标。
推进驱动 ReAct、固定评审、验证分支、事件响应。 拥有必要控制状态，不拥有模型厂商或 Sandbox 实现。
工具 schema、参数校验、结果呈现与操作语义。 不自行扩大授权或伪造 Runtime 结果。
模型路由 模型选择和请求参数策略。 候选阶段可变；受理后原请求、原绑定固定。
观察 UI、统计、诊断。 只读已确认结果；普通观察故障不成为隐藏的业务提交屏障。

具名 Hook 明确顺序和权限：请求候选可按序改写；最终授权与完整性拒绝不能被后续普通扩展放宽；结果呈现不改原生结果；名称冲突须拒绝或显式替换。

Cordis 可管理依赖、作用域与进程内装卸，不能替代持久责任。卸载依次停止新调用、排空／交接已有调用、移除注册、清理临时资源。Work 的逻辑状态与未结操作在实例消失后仍存在。使用 Cordis 不是所有 Harness 的接入前提。

7.3 Work 目录与配置

work/
  work.toml          逻辑配置、确定 Harness 入口和资源声明；不含秘密
  harness/           源码或确定 release 引用
  surface/           可选，仅 Worksurface 等文件策略使用
  .loom/             Runtime 管理，非整体向模型开放
    durable.json     实际引擎的执行绑定，不是可复制的执行许可
    records/         原文、请求、结果、内容与历史保留引用
    versions.git/    Work 与获准副本的内容版本
    views/           固定范围的只读事实视图
    state.sqlite     可选查询索引；可重建，不作为第二套推进状态

Userspace            独立项目、用户资料与产物，位置由用户资源绑定决定
Runtime 私有存储      事件设施状态、权限、凭据和必要操作收据

只创建实际需要的目录。Surface 不是完整历史副本，Userspace 不随 Work 关闭而删除。T 的 work.toml 与服务配置见附录 A.6；其他入口使用明确的发布元数据，不默默套用 Workflow 字段。

7.4 版本与信任

Harness 候选通过 Git 分支、worktree 与普通代码维护；检查、发布、启用分别发生。恢复原执行使用原版本；换版本先确认状态兼容和未结操作的解释方式。编辑 Surface 只影响后续投影，不等于升级代码。

使用者批准的 Harness 可作为受信代码运行于共享 Worker，安全沙箱按信任需求选用；模型生成的任务 Bash 和项目脚本仍通过执行管控。模型生成新 Harness 不等于自动批准在受信宿主启用。
