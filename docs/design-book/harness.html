07. Harness：推进逻辑与组合

Harness 回答“怎样把问题持续推进到有依据的结果”。它组织每一步所需的信息、模型判断、实际行动和结果检查，并根据反馈决定下一步。控制流程可以由代码预先规定，也可以让模型在获准工具和停止条件内选择行动。

7.1 定义推进逻辑

职责 最小定义
目标与输入 要解决什么问题，接收哪些输入，何时把新信息纳入当前工作，以及如何记录处理结果。
信息与判断 为每一步选择什么信息、模型和工具，怎样检查模型的回答，以及哪些结论需要外部证据验证。
推进 如何衔接行动与检查，哪些步骤可以并行，失败后重试、改换方案还是停止，何时等待用户或外部条件。
上下文容量 信息持续增长时，选择摘要、检索、归档或有界保留。Runtime 提供容量和格式检查，Harness 决定保留哪些信息。
进度与完成条件 明确什么结果算完成，哪些业务状态是继续工作的依据；通过受管顺序代码或显式状态驱动交给 Runtime 保存和恢复。

以调研为例，Harness 可以先让模型列出疑点，再并行收集证据、检查相互冲突的结论，最后决定补查或交付。Runtime 保存各次调用和采集结果；中断后复用已完成的部分。决定“还缺什么证据”属于推进逻辑，保证“已有证据不会因中断而丢失”属于运行机制。

Harness 发布时须固定入口、代码版本、状态格式、所需能力及依赖。输入交付、操作核对、调度和权限检查由 Runtime 提供，作者通过公开契约使用。

7.2 组合与替换策略

能力 可替换什么 状态／权限边界
上下文 会话＋archive、Surface、检索或批量片段。 同一次模型请求的内容选择由一个明确组件负责；多个裁剪策略必须协调，避免互相覆盖选择。
推进驱动 ReAct、固定评审、验证分支、事件响应。 保存推进所需的业务状态，通过 Runtime 调用模型和执行环境。
工具 schema、参数校验、结果呈现与操作语义。 不自行扩大授权或伪造 Runtime 结果。
模型路由 模型选择和请求参数策略。 提交前可以调整；Runtime 受理后保存原请求和原服务绑定，恢复时不重新选择。
观察 UI、统计、诊断。 读取已确认结果。若观察组件不承担验收责任，它的故障不应阻止业务结果提交。

扩展点（Hook）须明确调用顺序和可修改的内容。提交前的请求可以依序调整；授权与完整性检查一旦拒绝，后续普通扩展不能覆盖拒绝结果。结果展示可以加工，但须保留原始返回。注册名称冲突时拒绝或要求显式替换。

Cordis 可用于管理依赖、作用域和进程内组件，并非必需依赖。卸载组件时，先停止接收新调用，再完成或转交已有调用，最后移除注册并清理临时资源。Work 的状态和未完成操作仍由 Runtime 保留。

7.3 Work 目录与配置

work/
  work.toml          逻辑配置、确定 Harness 入口和资源声明；不含秘密
  harness/           源码或固定发布版本（release）引用
  surface/           可选，仅 Worksurface 等文件策略使用
  .loom/             Runtime 管理，非整体向模型开放
    durable.json     实际引擎的执行绑定，不是可复制的执行许可
    records/         原文、请求、结果、内容与历史保留引用
    versions.git/    Work 与获准副本的内容版本
    views/           固定范围的只读事实视图
    state.sqlite     可选查询索引；可重建，不作为第二套推进状态

Userspace            独立项目、用户资料与产物，位置由用户资源绑定决定
Runtime 私有存储      事件设施状态、权限、凭据和必要操作收据

只创建实际需要的目录。Surface 不是完整历史副本，Userspace 不随 Work 关闭而删除。Temporal 参考组合 T 的 work.toml 与服务配置见附录 A.6；其他执行组合须声明自己的配置格式和发布元数据。

7.4 版本与信任

Harness 代码可通过 Git 分支和 worktree 维护。保存修改不等于启用：候选版本先验证，再发布和选择。恢复原执行须使用原版本；升级前检查状态兼容性，以及新版本如何处理已有操作。Surface 的内容修改只影响后续上下文选择。

经使用者批准的 Harness 可在共享 Worker 中作为受信代码运行；不受信代码须按部署要求隔离。模型生成的任务 Bash 和项目脚本仍通过受控执行入口。模型生成的 Harness 代码也须经过验证和批准，才能在受信宿主启用。
