01. 目标与范围

Loom 让模型参与的工作能够持续推进，直到问题解决，或有明确理由等待、停止。一次模型调用可以给出判断、方案或工具请求；复杂问题还需要取得新证据、执行行动、检查结果，并据此决定下一步。

Harness 定义如何推进。 它把模型调用、工具操作和结果检查组织成连续过程：每一步依据什么信息，哪些工作可以并行，遇到失败如何调整，何时需要用户参与，以及怎样判定任务完成。模型可以参与这些决定；Harness 负责把决定接成可执行的过程。

Runtime 提供推进所依赖的运行能力。 它接入获准的信息和服务，准备执行环境，落实权限与资源限制，保存进度和操作结果，并在等待结束或运行中断后恢复执行。更换解题策略时，这些能力及其可靠性约定应当继续适用。

例如，调研一个问题可以按“收集资料 → 比较证据 → 补查疑点 → 验证结论”推进。Harness 决定查什么、如何判断证据和何时收敛；Runtime 负责取得获准资料、执行调用、保存结果，并在进程重启后接续未完成的步骤。批量评审和事件监控也遵循这个分工，只是推进方式不同。

1.1 Runtime 承担什么

共同需要Runtime 的责任Harness 的决定
取得信息与调用模型读取获准资料，接收用户或外部来源的变化，调用模型；保留来源、版本和实际返回。哪些信息与问题相关，何时采用，怎样组织模型上下文。
准备环境与执行操作按任务要求取得环境和工作副本，检查所需能力，执行获准操作并返回结果。需要什么环境和工具，要执行哪些行动。
约束影响范围执行宿主授予的文件、网络、服务和预算限制；权限或隔离能力不足时拒绝派发。在已获准范围内选择行动；需要扩大范围时提出请求。
中断后恢复与持续等待保存已确认进度、操作身份及待办；复用已有结果，核对未知结果，在条件满足后安排继续。保存哪些业务状态，等待什么，以及恢复后进入哪个业务分支。
保留依据与产物保存必要内容及历史版本，提供可追溯读取和受控整合。如何使用历史、评价产物，以及是否提出整合或发布请求。

这些责任不要求每份 Harness 调用全部接口。只做评审的程序可能不需要命令环境，但仍需要模型访问、结果保存和中断恢复；监控程序可以先按规则筛选事件，只在需要判断时调用模型。

安全边界以实际授权和执行限制为准。Harness 的指令不能自行扩大权限；Runtime 也不能仅凭一次模型判断，保证任意行动没有危害。部署必须说明可限制的资源、隔离范围及无法提供的能力。

1.2 设计必须满足的条件

目标可检验的结果
推进策略可替换改变上下文选择、工具组合或控制流程，不要求重写输入交付、模型适配和恢复机制。
工作跨越进程寿命已受理输入、已确认结果和未完成事项在进程退出后仍可恢复；设施恢复或等待条件满足后自动安排继续。
决策与受控执行分工明确Harness 提出行动，Runtime 检查授权并通过模型服务或执行后端落实；任务代码不能取得管理端权限。
等待不占用专属执行资源纯等待不保留每个 Work 的 Agent 进程、模型连接或空转 Sandbox；必要状态由共享服务和存储保留。

优先复用成熟组件。先满足可靠性、安全边界和使用契约，再优化速度与资源占用。事件驱动用于离线接收和按需唤醒；具体组件选择见实现接入与选型依据。

以上是设计接口，各操作使用所属 Work 的身份，并受相应授权与预算约束。Harness 可以用顺序代码、显式状态或模型循环组织推进；Surface 和全局聊天记录都不是接入前提。作者需要定义的内容见Harness 定义。
