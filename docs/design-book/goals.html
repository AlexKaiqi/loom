01. 目标与范围

Loom 是供不同 Harness 共用的持久运行底座。Harness 编写工作逻辑；Runtime 提供输入、模型、执行、内容和持久等待。 模型自主循环、批量评审程序和事件监控程序都直接使用这些能力。

核心目标 必须能观察到的结果
多样 Harness 共用底座 更换上下文策略、工具或控制流，不要求重写事件、模型适配和恢复机制。
Durable 已受理工作和已确认进度跨越进程寿命；设施恢复或条件满足后，系统自动安排继续。
控制与任务执行分离 Harness 决定做什么；模型服务和 Sandbox 执行实际操作。任务执行可以在本机或远端。
非执行期释放专属资源 纯等待不保留每 Work 的 Agent 进程、模型连接或空转 Sandbox；共享服务、存储和有界缓存仍有成本。

1.1 实现原则

优先复用成熟开源组件，也允许抽取和修改其实现。稳定可靠优先于极致性能；接口尽量符合普通代码、文件和异步调用的习惯。 速度、资源占用和复杂度在满足契约的方案之间优化。

事件驱动是实现离线接收、按需执行与独立协作的手段，不是独立产品目标。NATS、Temporal、Cordis、Resonate 等组件的职责与采用范围见附录 A和附录 B。

1.2 底座对作者开放什么

我要做什么 使用的入口 谁决定业务含义
关心某种变化，离线时也接收 events.subscribe，inputs.next Harness 决定收到以后做什么。
发布一份结果或观测 events.publish 事件类型定义载荷含义；发布不等于对方验收。
调用一次模型 model.invoke，或 submit + result 调用者提供输入；是否继续调用由调用者决定。
运行命令、编辑任务文件 tools.call／execution.submit 工具定义业务接口，Provider 落实执行。
等待输入、结果或时间 受管 next／result／sleep Harness 定义等待条件和后续分支。
读取资料、保存产物、查历史 content、history、只读事实视图 读取不自动消费输入，保存不自动发布或验收。

所有入口使用同一 Work 的身份、授权和预算。底座没有必需的 runAgent(prompt)，也不要求 Surface 或一份全局聊天记录。
