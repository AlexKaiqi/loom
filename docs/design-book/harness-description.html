08. Harness 描述与作者入口

本章定义作者怎样把推进程序交给 Runtime：代码描述固定可运行材料和许可入口，入口约定说明程序如何使用受管能力，Work 配置声明初始调用及逻辑资源。这些是目标契约；具体装载、隔离执行和恢复机制见Harness 执行管理，示例不表示 SDK 已发布。

Harness 可以由作者预先编写，也可以由正在运行的 A 让模型生成 B。两者提交相同描述并使用相同调用契约；无需先发布发行包或重新部署整个 Runtime。推进策略和动态调用的行为见第 7 章。

8.1 作者提交什么

code_ref 指向一份固定的 HarnessCodeDescriptor。描述与所引用的源码、依赖及必要能力材料均使用不可变内容；文件路径、同名分支和 latest 不足以固定正在运行的版本。业务输入由独立的 input_ref 提供，不混入代码描述。

作者材料确定含义
source_ref固定源码或可执行内容。许可入口须能从该版本装载；候选文件的后续编辑只影响新调用。
sdk_ref声明所需 Loom SDK 契约与版本约束。它不是宿主凭据，也不替代 Runtime 对实际 SDK 内容的固定。
dependency_ref固定依赖快照及其获取依据；恢复不能重新解析远程最新版本。
entries允许调用的入口与作者形式。managed_sequence 使用受管 SDK；state_step 使用有限推进约定并声明 state_schema。
requirements_ref可选的必需运行能力声明。Runtime 核验它与获准环境是否相容；声明不能授予网络、文件、模型服务或额外预算。
代码描述类型 · harness-code-contracts.ts
import type { Ref } from './event-contracts';
export type HarnessCodeDescriptor = {
  format: 'loom.harness-code';
  version: 1;
  source_ref: Ref;
  sdk_ref: string;             // 所需 Loom SDK 契约／版本约束，不是宿主凭据
  dependency_ref: Ref;         // 锁定依赖及获取依据，不能是 latest
  entries: Record<string,
    | { mode: 'managed_sequence'; state_schema?: number }
    | { mode: 'state_step'; state_schema: number }>;
  requirements_ref?: Ref;     // 必需运行能力；不能据此扩大授权
};

Runtime 根据这份描述、调用请求和受信授权生成 HarnessBinding：保存实际 SDK、依赖、编译产物、环境、有效范围与恢复绑定。作者不填写引擎管理地址、Worker 队列或私有凭据；描述中的 SDK 约束也不能覆盖已受理调用的实际绑定。

图映射和结构定义可以作为同一 Harness 版本的材料保存，按图结构契约固定其规则与来源。它们是可选的表达材料，不决定执行身份与权限，也不替代可运行代码的描述。

8.2 受管顺序入口

managed_sequence 入口以 main(work, input) 形式编写控制流程。input 是 Runtime 根据固定 input_ref 装载的业务输入；work 提供当前调用获准的模型、工具、内容、事件、输入、等待和 Harness 调用入口。业务输入的校验和返回结果的含义由这份 Harness 定义；Runtime 保存结果与剩余责任，不以返回值代替业务验收。

作者通过受管 SDK 取得非确定信息和执行外部操作，再用顺序、分支或并发组织结果。执行绑定记录稳定操作身份、已确认结果与等待，恢复原控制流程；作者不手工拆分 continuation，也不维护第二份推进游标。普通网络 Promise、可变文件读取和 Shell 内存不自动具有持久语义；需要跨中断复用的结果须经过受管入口。

子 Harness 默认只取得固定调用输入，不自动接收父调用聊天记录或 Work 邮箱。显式转交已领取输入使用 inputs.transfer；并发、等待、取消和结果责任按Harness 调用契约处理。A→B→C 的调用轨迹与代码片段见生成与组合示例。

8.3 显式状态入口

state_step 入口接收 Runtime 根据 input_ref 装载的固定业务输入，以及同次推进固定的 frame。首次 frame 的 state 为 null、base_revision 为 "0"，作者据固定业务输入构造符合 state_schema 的首个状态；此后使用上一份已确认状态。原操作结果、获准输入批次和执行 fence 均由 Runtime 提供；结果和输入只是当前调用获准的范围，不是全部 Work 邮箱或历史。入口只作一次有限纯计算，返回新状态、操作意图以及等待或业务结果，不直接调用 SDK、网络、模型、工具或子 Harness。

State step 类型 · state-step-contracts.ts
import type { Json, Ref, InputDelivery } from './event-contracts';
import type { HarnessOutcome } from './harness-contracts';
export type AdvanceFrame = {
  run_id: string;
  binding_ref: Ref;
  state_schema: number;
  state: Json;
  base_revision: string;
  saved_results: Array<{
    operation_id: string;
    outcome_ref: Ref;
    value: Json;              // 原操作 DTO；大载荷仍以 Ref 表达
  }>;
  batch_deliveries: InputDelivery[];
  fence: string;              // Runtime 给出；函数原样返回，不能自行生成
};
export type AdvanceIntent = {
  method: string;             // 已登记的受管端口方法，不是任意 RPC 方法
  request: Json;              // 对应方法的请求 schema，去掉 Runtime 身份／请求键字段
};
export type AdvanceWait =
  | { kind: 'operations'; join: 'all' | 'any';
      operations: Array<
        | { operation_id: string; intent_index?: never }
        | { intent_index: number; operation_id?: never }>; }
  | { kind: 'inputs'; filter: { subscription_id?: string; types?: string[] } }
  | { kind: 'until'; deadline: string };
export type AdvanceDecision = {
  base_revision: string;
  fence: string;
  state: Json;
  intents: AdvanceIntent[];
} & (
  | { wait: AdvanceWait; result?: never }
  | { result: HarnessOutcome['business_result']; wait?: never }
);
// Runtime 先按 input_ref 装载固定业务输入；此入口只进行一次有限纯计算。
export type StateStepEntry = (input: Json, frame: AdvanceFrame) => AdvanceDecision;

intents 按数组顺序持久登记，以该阶段及意图位置形成稳定身份；函数不能自行生成 Operation 身份、请求键或派发。同批次意图的请求必须自足且可共同登记，独立外部操作可以并行，保存的顺序不随完成顺序改变。需要依据某项结果或确认停止决定后续请求时，先等待原操作，再由下一 frame 计算；跨阶段的先后关系由已保存推进状态确定，不另设批次执行器或预填未知结果。intent_index 是本次数组的零起始位置；等待列表非空、引用有效，deadline 使用明确时区的绝对时间。输入等待仍使用当前 scope 的领取规则。

Runtime 检查原 base_revision、fence、状态 schema、方法请求与授权，将新状态、操作身份、等待或业务结果在同一持久决定中确认。inputs.complete／inputs.transfer 等控制意图直接在这一被接受的推进提交中核对并确认，不作为稍后可重试的外部效果；不能先保存新状态，再单独改变输入处置权。模型、工具、Harness 启动等外部意图登记 Operation 后由已有机制派发；需要其回执或结果才能处置输入时，等待原操作，再由下一 frame 作决定。等待与业务终态互斥；业务结果同时有未结操作时，沿用 HarnessOutcome 的责任接管要求。重复推进复用已接受的决定；旧修订或旧执行者不能再次提交。AdvanceIntent.request 使用已有模型、工具、内容、事件、输入和 Harness 端口的请求 schema，受信身份与请求键仅由 Runtime 填入；意图若自行携带这些字段、使用未知方法或不相容请求，在阶段提交前拒绝，不维护另一套语义相似的操作定义。

8.4 初始 Work 配置

Work 配置声明初始 Harness 的代码引用、入口、逻辑执行环境、模型服务和任务资源；宿主配置决定实际服务、版本及授权。下面是与执行引擎无关的 work.toml 目标结构 4；动态子调用使用同样的 Harness 请求契约，不要求为每份新代码发布 Worker 或建立新 Work。示例中的逻辑引用均须先解析，不能把未验证的组合标成可用。

schema_version = 4

[harness]
code_ref = "harness:basic@locked"
entry = "main"
environment = "harness-js"

[runtime]
service = "primary-runtime"

[model]
service = "primary-model"

[userspaces.app]
resource = "project-app"
access = "write"
delivery = "per-tool"

[targets.default]
profile = "local-default"
userspaces = ["app"]

code_ref 解析为本章规定的不可变代码描述及材料；描述中的许可入口决定 mode、state_schema 和依赖要求，宿主解析实际 SDK、依赖摘要、运行时与执行绑定。Basic 不要求 [surface]；Worksurface 入口要求其 Surface 资源。Work 只声明逻辑资源，物理目录、引擎端点与私有 credential_ref 留在宿主。结构 3 的 T 专用 workflow_type 不再属于公开 Harness 配置；迁移时解析原预装代码与绑定，不静默把它变成动态顺序程序。

工具使用的 targets 声明用户环境；harness.environment 声明执行推进程序所需的逻辑环境，两者分别核验入口和资源范围。需要给一个 Target 提供多个 Userspace 时，可采用下面的公开配置片段；app 与 reference 均须有相应资源声明和授权。

# work.toml 结构 4 的默认 Target 配置片段。
[targets.default]
profile = "local-default"
userspaces = ["app", "reference"]

公开逻辑配置不包含秘密、物理目录、原生资源 ID 或执行引擎连接。宿主服务与实际 Profile 的解析见组件拼接与宿主配置；代码保存、版本固定与运行权限分别确认，不能靠复制配置取得原调用的执行权。

8.5 生成、调用与结果检查

  1. 编写或生成程序，选择受管顺序或显式状态入口，定义业务输入、状态格式及结果判断；只使用当前调用获准的受管能力。
  2. 保存固定代码与依赖材料，形成完整代码描述并取得 code_ref。图定义按需要另保存为同版本材料，不能替代代码或实际运行依据。
  3. 在创建 Work 时声明初始入口，或从已有调用通过 harness.start 提交固定代码、入口、输入、逻辑环境与收窄限额。启动回执确认 Runtime 已承担责任；丢失回执时核对原键，不换键重启。
  4. 使用 result 等待结果，使用 inspect 核对绑定、阻塞和未结责任，再按本 Harness 的完成条件检查产物。保存业务结果、确认实际停止和结清责任分别判断。

不可装载的代码或入口返回 invalid_code，缺失依赖返回 dependency_unavailable，作者形式或 SDK 接合不相容返回 unsupported_binding。尚未解析的配置返回 not_ready；原版本无法恢复时保留责任并报告 recovery_incompatible 或具体阻塞原因。授权、限额和重复请求仍按共同规则检查，完整失败与调用类型见第 11 章。
