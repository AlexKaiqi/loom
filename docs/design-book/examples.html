08. 参考 Harness

以下示例展示同一 Runtime 上的不同推进方式：Basic 根据模型的工具请求循环，Worksurface 用文件维护长期理解，评审程序按固定流程并发检查。它们复用相同的输入、模型、执行和恢复契约；具体 SDK 与发布状态须由实现说明。

8.1 Basic：模型与工具循环

Basic 把任务指令和已有交互组成模型上下文。模型请求工具时，Harness 通过 Runtime 执行 Bash 或精确编辑，收集结果后再次调用模型；模型正常回答且未请求工具时结束本轮。上下文增长时，由模型主动调用 archive 整理。该策略不需要 Surface。

模型／工具结果 驱动动作
正常完整响应含 tool call 验证并执行工具，为每项调用记录对应结果，再调用模型。
正常完整响应无 tool call 交付回答，结束本轮；Work 继续开放。
文本与 tool call 同时存在 仍按工具路径继续，不以已有文本提前结束。
截断、取消、错误、未知结果 保存实际状态。按策略修复或等待；重试须先满足原操作的核对规则，不能将这些状态当作正常完成。
明确 yield 保存当前进度与等待条件，释放本轮执行资源。 
// runBasicTurn 的内部模型／工具调用都使用受管原语。
while (true) {
  const next = await work.inputs.next({});
  if (next.kind === "closed") return;
  const replyRef = await runBasicTurn(work, next.delivery.input);
  await work.inputs.complete(next.delivery, {
    outcome: "handled", result_ref: replyRef
  });
}

Bash 默认按独立命令执行，工作目录和环境变量显式传入，继续所需状态保存到文件。需要持久终端时另行启用会话能力；终端连接本身不提供中断恢复保证。

Archive 工具： archive({through, summary})。模型根据上下文反馈选择归档位置 through，在摘要中保留任务要求、更正、进度、未决事项和原文引用；归档实现检查消息完整性和容量后提交新选择。

契约点 规则
状态 {revision, after?, summary_ref?}，由 Harness 的持久状态保存；不新增 history／archive 目录。
保护 当前必需输入、当前 archive 调用、尚未配齐结果的工具调用，以及不可拆分的原生消息块必须保留。较早且已完整记录结果的工具组可以归档。
生效 先保存摘要和候选选择，检查工具调用与结果是否配对、上下文是否超限，再同时提交选择与工具结果。下一次请求使用新 revision。
查回 历史与原文保留，通过 history／只读事实视图读取；不是重跑旧工具。
失败 返回具体范围和原因；失败时保留原选择，不报告已归档，也不自动切换摘要策略。

Runtime 在上下文窗口尚有整理余量时，反馈预计输入量、预留输出量、各来源占用及可归档位置。模型忽略提示或必需输入过大时，保存修复状态并停止发送超限请求。摘要质量必须用真实长任务检验，机制本身不保证摘要无遗漏。

8.2 Worksurface：文件化理解与协作

Worksurface 复用 Basic 的模型与工具循环，通过 Surface 文件维护当前理解和上下文选择。它替换 Basic 的 after / summary 状态，避免两份选择互相冲突。多 Work 协作是可选能力，协作者也可以使用其他 Harness。

## 历史选择
```facts

```

主模板只解析 include 和 facts 代码块，不执行 Shell、SQL、循环或递归模板。include 固定授权资源、文件版本和可选行范围；facts 只有一块，支持 after、include、body_refs。未知字段和非法范围返回定位错误。

模型通过编辑文件调整选择。Runtime 分别记录文件已修改、上下文校验通过和请求实际采用的版本。校验失败时保留候选文件，并报告定位信息；原上下文仍有效且能容纳诊断时，可以用它发起明确的修复步骤，否则暂停推进。每次请求都保留内容来源及版本。

协作采用第 3 章同一事件契约：验证方预先订阅 → 制作方发布候选 → 验证方取得输入并返回对应版本的报告 → 发起方决定是否采用。创建 Work、定向交付与取消是获准操作；父子关系不自动授予权限、预算或级联终止。

8.3 普通代码：评审管线与修改 Agent

Harness 先固定文档版本、评审标准、输出格式和各段落的标识，再限制并发数进行评审。它按评审项标识汇总报告，交给修改 Agent 生成新版本，然后再次评审。每次调用使用独立上下文和操作记录；这些步骤可以在同一 Work 中完成。

固定文档 v7 和评审清单
  → 并发检查各章节／段落／句子（独立 ModelRequest）
  → allSettled 汇合：失败／拒绝／格式错误不算“没有问题”
  → 完整报告 + 原文版本 → 修改 Agent
  → 保存 v8 → 新评审轮次；达到上限则明确停止

假设 100 个评审项完成 37 项后进程退出，Runtime 保留这 37 项结果，逐项核对剩余操作后继续。修改 Agent 内的模型和工具调用也须分别记录，才能从中断位置恢复；不能只在整个修改循环结束时保存一个结果。

事件监控采用另一种推进方式：订阅变化，取得输入后按规则判断，需要进一步分析或行动时才调用模型或工具，最后记录处理结果。没有待处理输入时，Runtime 保存等待条件并释放执行资源。
