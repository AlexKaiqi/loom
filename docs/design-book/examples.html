09. 参考 Harness

以下示例展示同一 Runtime 上的不同推进方式：Basic 根据模型的工具请求循环，Worksurface 用文件维护长期理解，评审程序按固定流程并发检查，生成程序还可以启动下一份 Harness。它们复用相同的输入、模型、执行和恢复契约。代码展示目标 SDK 的操作形态，不表示已发布或可直接执行；实际入口见对应版本的实现说明。

9.1 Basic：模型与工具循环

Basic 把任务指令和已有交互组成模型上下文。默认工具为 Bash、精确编辑与上下文整理；模型请求工具时，Harness 通过 Runtime 执行相应操作，收集结果后再次调用模型，正常回答且未请求工具时结束本轮。上下文增长时，由模型主动调用 archive 整理。该策略不需要 Surface。

模型／工具结果 驱动动作
正常完整响应含 tool call 验证并执行工具，为每项调用记录对应结果，再调用模型。
正常完整响应无 tool call 交付回答，结束本轮；Work 继续开放。
文本与 tool call 同时存在 仍按工具路径继续，不以已有文本提前结束。
截断、取消、错误、未知结果 保存实际状态。按策略修复或等待；重试须先满足原操作的核对规则，不能将这些状态当作正常完成。
明确 yield 保存当前进度与等待条件，释放本轮执行资源。 
// runBasicTurn 的内部模型／工具调用都使用受管原语。
while (true) {
  const next = await work.inputs.next({});
  if (next.kind === "closed") return;
  const replyRef = await runBasicTurn(work, next.delivery.input);
  await work.inputs.complete(next.delivery, {
    outcome: "handled", result_ref: replyRef
  });
}

Basic 向模型展示Sandbox 内的 Bash 工具，由 Harness 接到 Runtime 的受管执行入口。连续调用使用同一获准工作副本或已确认的新内容版本；工作目录和环境变量每次固定，上一条命令的 cd/export 不隐含延续。需要保留环境中的工具或服务时使用 Sandbox 公开会话；需要同一 Shell 或 PTY 时另核验对应能力，两者都不能代替 Work 的中断恢复。

模型可见的工具集合由 Harness 决定。只展示 Bash 时，获准 Work 环境中的 Loom CLI 也可发起保存内容、启动 Harness 与查询结果；命令仍进入同一受管操作契约。Bash 的选择不决定 Harness 的代码运行环境，Shell 进程也不拥有子 Harness 的持久调用身份。

Archive 工具： archive({through, summary})。模型根据上下文反馈选择归档位置 through，在摘要中保留任务要求、更正、进度、未决事项和原文引用；归档实现检查消息完整性和容量后提交新选择。

契约点 规则
状态 {revision, after?, summary_ref?}，由 Harness 的持久状态保存；不新增 history／archive 目录。
保护 当前必需输入、当前 archive 调用、尚未配齐结果的工具调用，以及不可拆分的原生消息块必须保留。较早且已完整记录结果的工具组可以归档。
生效 先保存摘要和候选选择，检查工具调用与结果是否配对、上下文是否超限，再同时提交选择与工具结果。下一次请求使用新 revision。
查回 历史与原文保留，通过 history／只读事实视图读取；不是重跑旧工具。
失败 返回具体范围和原因；失败时保留原选择，不报告已归档，也不自动切换摘要策略。

Runtime 在上下文窗口尚有整理余量时，反馈预计输入量、预留输出量、各来源占用及可归档位置。模型忽略提示或必需输入过大时，保存修复状态并停止发送超限请求。摘要质量必须用真实长任务检验，机制本身不保证摘要无遗漏。

9.2 Worksurface：文件化理解与协作

Worksurface 复用 Basic 的模型与工具循环，通过 Surface 文件维护当前理解和上下文选择。它替换 Basic 的 after / summary 状态，避免两份选择互相冲突。多 Work 协作是可选能力，协作者也可以使用其他 Harness。

## 当前进度


## 历史选择
```facts
after = "F0120"
include = ["F0118"]
body_refs = ["F0134"]
```

主模板只解析 include 和 facts 代码块，不执行 Shell、SQL、循环或递归模板。include 固定授权资源、文件版本和可选行范围；facts 只有一块，支持 after、include、body_refs。未知字段和非法范围返回定位错误。

模型通过编辑文件调整选择。Runtime 分别记录文件已修改、上下文校验通过和请求实际采用的版本。校验失败时保留候选文件，并报告定位信息；原上下文仍有效且能容纳诊断时，可以用它发起明确的修复步骤，否则暂停推进。每次请求都保留内容来源及版本。

协作采用第 3 章同一事件契约：验证方预先订阅 → 制作方发布候选 → 验证方取得输入并返回对应版本的报告 → 发起方决定是否采用。创建 Work、定向交付与取消是获准操作；父子关系不自动授予权限、预算或级联终止。

9.3 普通代码：评审管线与修改 Agent

Harness 先固定文档版本、评审标准、输出格式和各段落的标识，再限制并发数进行评审。它按评审项标识汇总报告，交给修改 Agent 生成新版本，然后再次评审。每次调用使用独立上下文和操作记录；这些步骤可以在同一 Work 中完成。

固定文档 v7 和评审清单
  → 并发检查各章节／段落／句子（独立 ModelRequest）
  → allSettled 汇合：失败／拒绝／格式错误不算“没有问题”
  → 完整报告 + 原文版本 → 修改 Agent
  → 保存 v8 → 新评审轮次；达到上限则明确停止

假设 100 个评审项完成 37 项后进程退出，Runtime 保留这 37 项结果，逐项核对剩余操作后继续。修改 Agent 内的模型和工具调用也须分别记录，才能从中断位置恢复；不能只在整个修改循环结束时保存一个结果。

事件监控采用另一种推进方式：订阅变化，取得输入后按规则判断，需要进一步分析或行动时才调用模型或工具，最后记录处理结果。没有待处理输入时，Runtime 保存等待条件并释放执行资源。

9.4 A 生成 B，B 再运行 C

目标是对固定文档执行 100 项检查。A 是正在运行的 Harness；它让模型编写评审管线 B，B 调用检查 Harness C，再把完整报告交给 A。三者默认属于同一 Work，使用同一工作授权和预算；子调用的限制只可收窄。C 若需要独立接收长期事件、独立授权或独立关闭责任，才创建新 Work。

阶段操作与确认
固定输入并生成代码A 保存文档 v7、检查清单和已选 C 的固定代码引用；经受管模型调用生成 B。模型结果与候选源文件先保存，再形成不可变代码描述，声明入口、作者形式、SDK、依赖和状态格式；输入描述关联 C 与 100 个稳定检查项。
受理 BA 通过 harness.start 提交代码和输入引用。Runtime 校验入口、依赖与获准环境，固定实际绑定后保存原启动 Operation 和 run_id。首个参考环境为 JS／TS、固定 Node 与 Loom SDK 的 Linux 隔离环境；预授权范围内可自动启动，启用共享受信 Worker 或提升权限另按授权规则批准。
B 运行 CB 读取固定调用输入，按每批最多 5 项启动 C。每个 C 有独立 run_id、输入和模型上下文；它的模型、工具及结果保存各自使用受管入口。B 通过 allSettled 保留每项成功、失败、拒绝和取消，失败不解释为检查通过。
持久等待与恢复A 等待 B、B 等待 C 时，SDK 保存等待和继续依据；纯等待释放对应专属进程及闲置环境。共享持久内核继续接收 C 的结果，按原版本装载 A／B 并自动推进；不要求父进程保持在线。
返回与结清C 保存检查结果，其操作逐项结清或由 Runtime 持久接管；B 固定含版本与各项状态的报告，完成或确认转交所有子调用责任后交付结果。A 取得 B 的已保存业务结果与责任状态，决定修订、重评或交付，再完成原 Work 输入；B／C 默认不争夺 A 的输入处置权。

以下片段从代码与输入已保存的位置开始。bCodeRef 和 bInputRef 来自 A 已记录的受管步骤；B 的 input 是 SDK 从固定 input_ref 装载的内容。内部 start 未手填键时，SDK 按持久调用日志分配稳定身份，重放返回原回执；不能仅以易变函数名或内存序号生成重试身份。

// A 的受管入口：生成并保存 B 后启动，等待原调用。
const b = await work.harness.start({
  code_ref: bCodeRef,
  entry: "main",
  input_ref: bInputRef,
  environment: "harness-js",
});
const report = await work.harness.result({ run_id: b.run_id });
// report.business_result.outcome 必须为 succeeded 才按成功报告采用；失败／取消保留原原因。

// B 的另一份固定代码：input 含文档版本、C 的代码引用与检查项。
export async function main(work, input) {
  const rows = [];
  for (let offset = 0; offset < input.items.length; offset += 5) {
    const batch = input.items.slice(offset, offset + 5);
    const settled = await Promise.allSettled(batch.map(async (item) => {
      const c = await work.harness.start({
        code_ref: input.c_code_ref,
        entry: "review",
        input_ref: item.input_ref,
        environment: "harness-js",
      });
      return await work.harness.result({ run_id: c.run_id });
    }));
    rows.push(...toReviewRows(batch, settled));
  }
  return { document_ref: input.document_ref, rows };
}
// toReviewRows 是纯格式映射：保留 item_id、调用结果与失败种类。
// fulfilled 只表示取得终态，仍须检查 HarnessOutcome.business_result.outcome。
// SDK 保存返回内容与终态；未结责任未确认时不报告调用已结清。

故障轨迹：B 受理后 A 未收到回执，恢复时重新进入原 start，取得同一个 B；同键改代码或输入则返回 identity_conflict。100 项完成 37 项后 B 退出，恢复复用这 37 项和原 C 调用，逐项续办或核对剩余项；若 C 已保存模型结果而工具尚未开始，仍从原工具清单继续。等待期间编辑 B 的工作区源码，只影响后续新调用，原 B 仍装载旧代码及依赖；原绑定不可用时明确阻塞。

结束与取消：等待超时或 race 不取消 B／C。A 决定停止时，用显式 self 或同 Work 的 tree 范围请求取消，再核对实际停止和已发生结果；关闭 Work 则先阻止所有所属调用的新意图，结清或确认转交原责任。没有稳定结果的外部操作保持未知，不能靠清理调用进程宣布成功停止。

展示：这条轨迹可按 Harness 的结构规则呈现为 A、B、各 C 及相关操作和内容的图。一个“本轮评审”结构可以折叠 100 个 C，但成员的原 run_id、文档版本、未结操作和跨结构关系仍可追查。结构的命名与识别规则随 Harness 定义和版本维护；展示契约见第 10 章，验收见H02—H08、G01—G03。
