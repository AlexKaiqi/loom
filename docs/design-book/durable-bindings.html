A.2 持久执行的实现

本页说明怎样用已有持久执行引擎落实恢复、等待与责任保留契约：继续依据保存在哪里，输入和到期条件怎样唤醒工作，以及中断后怎样复用结果。Harness 的代码描述见描述契约；代码装载、隔离、SDK 通道与临时进程管理见Harness 执行管理。这些宿主接合不能另持一套推进状态。

A.2.1 一份继续依据与已有引擎

创建 Work 时固定一套持久控制组合，统一裁决所有 Harness 调用的受理、继续、输入交接、取消和关闭。Work 与 run_id 是逻辑身份；引擎运行实例更换不创建新的业务调用。控制状态和必要引用按选定组合保存，原始内容与收据按内容契约保留；NATS 消费位置、runner 内存和查询索引不独立决定下一步。

组合继续依据与作者形式Loom 的接合责任
R：Resonate原生 promise／task 协议与受管调用日志；优先验证动态受管顺序代码。调用与内容身份、输入邮箱、原 Operation 核对、限域 SDK、长期记录与责任交接。动态隔离组合尚未验证。
T：TemporalHistory、Workflow 状态、Timer 与任务安排；分别覆盖预装 Workflow 和动态显式状态推进。输入受理与调用身份、推进提交、请求绑定、原操作核对；有限推进不替代受管顺序作者入口。
E：DSH／Cordis + 可嵌入内核所选内核的一份控制状态与责任记录；按实际内核声明作者形式。DSH 事件／投影／检查点与内核的适配、离线唤醒、阶段提交、操作收据；候选范围仍须验证。

受管顺序程序的控制位置由原生引擎恢复；显式状态程序的继续依据是已确认状态及后续待办。两种形式都不恢复任意进程栈或普通 Shell 内存。子调用可以选择其他获准运行环境，但必须接入本 Work 的同一控制组合；不相容时受理前返回 unsupported_binding。需要另一控制组合时，建立有独立责任的 Work，通过已有跨 Work 操作协作。

A.2.2 Harness 执行与持久控制的接缝

调用 DTO确定一次请求，执行管理的受理准备确定其实际代码、依赖、SDK、环境和恢复绑定。本页的控制组合接管稳定 run_id、初始状态和后续责任后，才安排运行。调度不重新解析候选目录或当前 Profile；装载失败留下原调用及阻塞原因。

控制边界接合要求
操作受理与结果复用受管步骤绑定稳定 Operation 及原请求；派发责任先保存。重入先查原回执，复用已确认结果；结果未知时核对原目的地，不能因引擎重试而换键重发。
输入与等待输入受理、处理权和等待状态在选定组合中保存。检查已有输入与登记等待之间不能丢唤醒；离线时受理的输入仍须安排继续。事件桥取得 InputReceipt 后 ACK，见事件实现。
Timer 与取消首次确认固定到期时间和计划版本，恢复不重新计时；到期、取消与输入准入按同一控制顺序裁决。取消控制位置不证明外部动作已停止。
执行所有权由原生 task fence 或推进修订拒绝旧执行者提交。fence 保护控制状态；已派发命令的写入和停止仍由原 Operation 与执行设施核对。
返回与交接保存业务结果时，未结操作必须已结清或由有权承接者持久接管。引擎 promise／Workflow 终态不把未知效果改为成功。

输入邮箱、同键内容冲突、取消竞争和责任交接是 Loom 的组合要求；引擎具有消息、Promise 或 Timer API 不等于这些接缝已经成立。输入处理权的转交由输入契约定义，本页只负责用所选控制状态落实其原子确认与后续唤醒。

A.2.3 T：预装 Workflow

Temporal Service 保存 History 并安排任务；Workflow Worker 执行预装 Harness Workflow，Activity Worker 接受单次模型、内容或用户环境操作。两种角色可同进程或分部署，不是一 Work 一进程。Worker 的固定代码、部署认证和可访问资源由执行接合约束，队列名不授予文件权限。

预装方式使用 Worker 创建时固定的 Workflow 代码，不能直接承诺执行运行时生成的 Harness B。也不能把 B 整体放入一个可重试 Activity，就声称内部的模型、工具、等待和子调用均已受管。Worker 装载依据。

proxyActivities 安排标准 Activity。Activity 通过 Runtime 的单次操作入口取得并保存结果后报告完成；Workflow 不裸读可变文件。Model Activity 不执行返回的 tool call，也不决定是否再次调用模型。

Loom 动作T 的映射与确认
启动StartWorkflow 固定 Work、Workflow 版本与配置。Harness 调用保留稳定 run_id，绑定记录保存引擎身份映射。禁止复用已关闭 Work 身份。
输入／控制短 loom.input／loom.control Update；COMPLETED 后才返回对应回执。handler 必须先安装，初始化未完成时返回 not_ready。
next／completeWorkflow 状态保存队列、处理身份、等待及处置；返回 delivery 的选择是已记录控制决定。
单次操作稳定 operation_id 绑定已保存请求；Activity 重入查原回执，是否派发由原操作状态决定。
Timer原生 Timer 加计划状态；到期、取消与输入登记按同一控制顺序裁决。
读取Query 读取应用状态，Describe 读取引擎状态；历史通过官方 API 与内容引用读取。离线视图声明覆盖位置。

消息及重放的上游依据分别见Temporal 消息接口和确定性约束。Update 受理输入不等待模型或业务完成；详细传输确认线保留在事件实现。

A.2.4 T：动态显式状态推进

固定版本的 genericWorkWorkflow 保存 Work 的调用关系、各 run_id 的状态与责任，调度固定 advanceHarness Activity。Activity 通过隔离装载接合调用原绑定的有限推进函数；候选代码不进入可信 Workflow Worker。

推进输入与输出遵守显式状态入口 ABI。通用 Workflow 检查 base_revision 和执行 fence，再把新状态、输入处置、稳定操作身份、等待及子调用责任作为一次控制决定登记；后续独立 Operation／Activity 才派发外部动作。过期修订或旧推进者的迟到结果拒绝提交。

有限推进不直接产生模型、工具、网络或子调用效果。重复计算没有外部效果，首次接受的结果进入 History 后恢复复用。后续 Activity 可能已经执行外部动作但未报告时，只核对原 Operation，不能生成新键。History 是继续权威，runner 内存和本地 JSONL 不是。

该接法覆盖显式状态作者形式。受管顺序作者不应自行拆 continuation 或手写状态机；不支持其形式的绑定在受理前返回 unsupported_binding，不能降低目标契约。

A.2.5 R：受管顺序代码的优先验证组合

Resonate 官方 TypeScript SDK 提供 generator 与 async／await 两种受管形式；async 形式通过 @resonatehq/sdk/async 与 ctx.run 取得 DurablePromise，普通外部 Promise 的 await 不自动记录。SDK 与约束依据。以下是待验证的组合接法，不是已完成支持的声明。

  1. 以稳定 run_id 建立原生持久调用，参数保存代码、入口、固定输入与实际绑定摘要。执行任务重新分配不改变这次逻辑调用。
  2. 原生 Context／SDK 保存受管调用日志、子调用结果和等待。Loom 的 model、tool、content、input、event 和 harness 入口接受管步骤，以日志中的逻辑调用身份派生稳定 Operation 键，恢复不使用新随机键。
  3. 隔离装载与 SDK 传输入口由执行管理提供；接合须保留原生日志、task fence 与挂起协议。普通 RPC Promise 不能代替持久等待，不另写重放解释器或 journal。
  4. 原生任务挂起后由共享调度设施承接输入、结果与到期唤醒；重新取得任务时按已保存日志重建到原步骤。输入邮箱、检查后登记等待及无在线 runner 的唤醒必须单独验证。
  5. 受管外部步骤接到 Loom 稳定 Operation。原生 promise 的取消或终态不覆盖原效果未知、费用未知或迟到结果；返回前须确认未结责任的承接。

先验证 A→B→C、部分并行完成、回执丢失、等待释放及原任务恢复，再确认这一组合可用。失败时修正接合，不能通过只支持预装函数或有限推进降低动态受管顺序代码目标。统一验收。

A.2.6 E：可嵌入内核的候选接合

DSH 的模型适配、上下文转换、工具 schema、响应分类与策略可作为 Harness 零件。完整 loop 的模型、工具、输入、等待与子调用改接受管原语；语义事件、投影和检查点接入所选内核。私有 Persistence／JSONL 不另成为能独立推进的权威，恢复消息关系也不证明业务输入已处理。

Cordis 可管理进程内依赖、scope 和装卸；无 Harness 在线时的输入与到期接续由持久内核承担，不能依赖 Fiber 存活。卸载中的进程资源由执行管理回收，已经开始的 Operation 仍由 Runtime 保留。只提供有限推进的内核须声明其覆盖显式状态，不能据此缩减顺序作者目标。

可嵌入内核仍是候选；其状态接合及唤醒、阶段确认和 fence 均须按相同轨迹验收。状态机研究入口。

A.2.7 历史滚动与故障接续

限制单次引擎历史长度时，先固定未结调用及代码绑定、输入和处理权、订阅关闭标记、计划、原回执、未结 Operation 与必要状态，再确认新运行实例接管。T 等 handler 完成后执行 Continue-As-New；R/E 必须用各自已验证的原生接续方式落实同一交接，不能只重启进程并清空日志。

旧回执和关闭标记可封存为不可变索引，当前运行保留增量；加载失败不等于不存在。引擎保留、内容 GC 与导出范围必须协调；历史已缺失时返回 history_gap 或明确阻塞，不能宣称完整恢复。业务关闭后，原回执、未知操作核对及持久清理接管仍可查询。

故障位置继续责任
已确认状态，尚未取得执行任务选定引擎保留任务并重新安排；不等待额外消息碰巧唤醒。
部分并行结果已保存日志或状态复用完成项，其余项分别继续或核对原操作；不重跑整个批次。
旧执行者迟到原生 fence／修订拒绝控制提交；Runtime 继续核对已经派发的外部动作。
滚动回执或目标状态无法确认核对原交接身份，保留未结责任；不能启动另一份独立推进权威。
