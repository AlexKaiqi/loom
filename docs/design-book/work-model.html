02. 工作模型与共同约定

Work 把一次次执行连接成同一项长期工作。本章定义工作中的对象，以及它们在重复请求、中断、并发和关闭时必须遵守的规则。

2.1 必要概念

对象 定义与边界
Work 一项持续工作的身份，以及所属配置、进度、记录和未完成事项。进程可以退出或更换，Work 仍然存在。
Harness 定义工作如何推进的程序：组织信息、模型调用、行动与结果检查，决定继续、等待或结束。每次运行固定代码版本，并使用约定的恢复入口。
Event / Input Event 是带来源和类型的发布记录；Input 是某个 Work 已受理的信息，必须记录处理完成、失败或忽略的结果。
Operation / Effect Runtime 已受理的一次操作，记录稳定身份、原请求、执行目的地、实际尝试及结果。模型调用、命令执行和事件发布都使用这一机制。
等待 已保存的继续条件，例如收到输入、操作完成或到达指定时间。条件满足前不要求 Harness 进程保持运行。
内容 / 上下文 内容包括资料、过程记录和产物；上下文是一次模型请求实际采用的信息。投影是按 Harness 的选择把内容组成上下文的过程及结果；Surface 是维护这种选择的一种文件形式。

Runtime 负责输入交付、模型访问、受控执行、内容保存与中断恢复。Provider 是它对接具体执行后端的适配器。Target 是 Work 声明的逻辑执行目标；Profile 是宿主为目标选择的配置；Allocation 记录一次实际分配的环境及其资源绑定。

Userspace 是由用户独立管理的项目、个人资料或数据资源。Work 使用其中获准的版本或工作副本；Work 关闭不删除原资源。

2.2 所有写操作共用的规则

契约 确定行为
C1 身份绑定 身份来自受信连接。request_key 在调用来源与目标 Work 的作用域内绑定方法和有效请求；不能复用为另一种操作。运行绑定保存解析后的默认值、内容及目的地。
C2 重复请求 同键同请求返回原回执；同键不同请求返回 identity_conflict。回执丢失后核对原键，不另造一次调用。相同正文配新键是新意图。
C3 回执 回执说明该次提交确认了什么，不代替对象当前状态。写入“已受理”不等于已开始、已完成或业务正确。
C4 恢复 已确认结果复用；未完成事项仍有执行或核对责任。超时和连接断开不能被解释成“从未执行”。
C5 授权 请求、历史读取和实际执行都核验所需权限；引用、队列名、目录名和业务标签不授予权限。旧回执的返回也须有读取权。
C6 一致确认 确认一个操作前，必须保存它所依赖的内容、状态和后续待办，并建立可恢复的关联。不能先报告成功，之后才尽力保存唯一必要内容。
C7 保留 未处理输入、在途操作、等待和已确认继续状态所需的记录受保护。归档上下文、卸载组件与回收环境不删除这些责任。
C8 可见失败 校验拒绝、资源不足、暂时不可用、结果未知分别返回稳定错误种类。没有确认结果的网络失败，仍需按原身份核对。

重复请求先核对原提交；有权读取时返回原回执，不因当前版本或生命周期已经变化而误报为一次新的过期操作。只有尚未提交的新请求，才继续检查当前执行所有者（owner）与预期版本。

request_key 不是 RPC 连接的 id，也不是模型生成的 tool-call ID。外部调用者重试时使用显式键；受管顺序代码可由持久执行绑定保存稳定调用身份。普通内存计数器或函数名不足以提供重启后的身份。

2.3 Work 不只有一个“运行状态”

状态维度 需要区分的状态
生命周期 open → closing → closed。等待不等于关闭。关闭须处置或转交未结事项。
输入 queued → processing → disposed。处理中可以等待或恢复；处置结果为 handled、failed 或 ignored。
操作 尚未派发、可能已经派发、结果已确认；取消请求与实际停止另行记录。
等待 未满足、已匹配、已取消／超时。得到答复不等于答复为批准。

Work 可以同时有待处理输入、某个未知操作和另一个已完成结果。结果未知的操作应阻止与它冲突的重发，但不必阻止无关的只读工作。界面可显示摘要，但不得用一个 done／failed 覆盖以上关系。

2.4 并发与顺序

控制状态有可确认的提交顺序，不等于操作必须串行。 同一 Work 可发起多个独立模型请求，每个使用自己的输入、操作身份和预算。共享文件写入按实际资源范围协调。

默认输入按目标 Work 的受理顺序取得；不从时间戳推导跨来源全局顺序。业务必须先 A 后 B 时，Harness 显式表达依赖。同一 Work 可以包含多次模型调用和多个任务；是否拆成独立 Work，由工作身份和责任归属决定。
