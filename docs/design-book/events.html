03. 事件与输入

3.1 接入变化并保留待处理输入

持续工作需要接收用户补充、其他 Work 的结果和外部系统的变化。Harness 声明关注的来源与类型；Runtime 在 Harness 离线时仍保留交付责任，待工作可以推进时提供输入。Harness 决定这些信息是否相关、如何处理，以及是否发布新的结果。

持久发布订阅把信息发布与接收解耦：发布者无需列出全部接收者，接收者也无需保持运行。事件服务负责把记录交到目标 Work；持久执行机制负责保存处理进度和等待状态。外部来源须先接入并获得读取授权，事件正文不能自证来源或授予权限。

3.2 发布、订阅与处理接口

以下为面向 Harness 作者的目标接口，方法与类型集中定义在第 11 章。events 负责前三个方法；inputs 是所有输入共用的处理接口。

方法 输入 成功确认 不确认
events.publish request_key, event_type, data 事件及其确定内容已持久保存，返回 event_id 和来源位置；系统承担有效订阅的后续交付。 不保证已有订阅者，不表示目标已受理或验收。
events.subscribe request_key, source, types, from 返回 subscription_id, start_cursor；订阅属于当前 Work，跨退出继续有效。 不启动业务回调，不自动创建目标 Work。
events.unsubscribe request_key, subscription_id 返回退订回执；目标 Work 已停止通过该订阅受理新输入关联。 不删除原事件，不撤销已有输入或在途操作。
inputs.next 可选 subscription_id / types 返回已绑定处理身份的 InputDelivery；无匹配项则持久等待。 不表示该输入已处理，不要求立即调用模型。
inputs.complete 原 delivery + outcome，可选 result_ref / reason 该输入已经明确处置，返回处置回执。 不声明业务成功，不取消它发起的未结操作。
inputs.transfer request_key, processing_ref, target_run_id 同 Work 的目标调用已承担原输入处理责任，返回目标绑定的新 processing_ref 与交接回执；来源处置权已撤销。 不完成业务处理，不授予目标普通 Work 邮箱消费权，不创建新 Work。

outcome 为 handled | failed | ignored。暂时故障或仍待回复时不要 complete：保留原处理并等待／重试。跨 Work 转交时，先按目标授权确认另一 Work 已接收独立输入，再完成当前输入；这是两份输入与各自责任。把同一 Work 已领取输入交给另一 Harness 调用，使用 inputs.transfer 交接原处理责任，不能让两个调用各自处置同一输入。

3.3 起点、筛选与取消

项 固定语义
source 一个已登记、获准读取的 Work 或外部来源；实际发布来源由 Runtime 绑定，不由正文自报。多来源使用多份订阅。
types 非空事件类型列表，精确匹配；例如 card.candidate.v1。不在事件服务执行任意 JS、SQL 或业务判断。
from: "now" 第一次成功登记时确认的来源起点，之后的事件进入订阅。回执给出实际 start_cursor；同键重入复用该起点，不重新计算“现在”。
from: {after: cursor} 从明确的来源位置之后补读。游标与来源及存储世代绑定；不可用范围返回 history_gap，不偷偷跳到最新。
订阅修改 相同键不能更改筛选或起点。需要变更时新建订阅、确认覆盖范围后退订旧订阅；重叠由目标去重。
退订后 next 先处理已受理且尚可取得的匹配输入；排空后返回 closed: subscription_closed，不无限等待。
退订与交付竞争 目标 Work 按确定顺序提交输入受理与退订。先受理则保留，先退订则拒绝新增关联；删除消息消费者不能代替这一确认。

events.inspect/list 返回自己的订阅状态、固定筛选和起点、积压或覆盖边界、最近失败；events.describe 返回获准事件类型的 schema、来源和发布含义。查询是读操作，不消费输入，也不修改游标。类型说明须足以让作者解释载荷和判断使用条件。

3.4 接收、重复与处理

情况 契约结果
B 的 Harness 未运行时 A 发布 有效订阅继续交付；B 的执行设施可用后自动安排推进，不等待用户再说一次“继续”。
信息早于 next() 到达 已在 B 的输入中，next 可以取得。早于订阅起点的信息不在该订阅范围内。
B 正在调用模型 普通输入先排队，不隐式打断或重入处理代码；Harness 在明确边界采用。
同一事件重复投递 同一目标只建立一个逻辑输入；相同身份、不同内容是冲突。
同一 Work 的两份订阅同时匹配 合并到同一输入，追加匹配关联；已被一个处理者认领或处置的输入不因新关联再处理一次。
两个不同 Work 订阅 各自有独立输入与处置；不是争抢一个任务。
next 已返回，进程退出 恢复原输入及处理关联。未完成输入不因读过而消失；旧执行者不能提交新进度。
已发布报告，complete 前退出 核对原发布键取得原报告事件，再 complete；不制造第二份报告。
订阅被撤权、目标关闭或历史缺失 返回具体原因和相关记录。已有输入与操作仍须处置；后续读取和执行继续受当前权限限制。

默认只有一个有效处理者认领某份输入。InputDelivery 携带不透明 processing_ref，SDK 自动传递，Harness 原样使用。complete 核对 Runtime 保存的原输入，不用回传正文覆盖输入。并发调用 next 可取得不同输入，但恢复同一次 next 仍绑定原输入。重新处理已处置输入需要新的业务请求，不靠重投触发。

同 Work 的 inputs.transfer 在一份持久决定中核对来源的有效处理权和目标的承接条件，再绑定目标 run_id、生成新的不透明处理身份、撤销旧身份，并保存向目标交付 delivery 的责任。目标通过自己的 inputs.next 领取；下一次普通 Work 输入仍需它单独具备邮箱消费授权。complete 同时检查当前调用 scope、处理身份和执行所有权；来源即使读取到新身份也不能冒充目标。

同键同内容重试返回原转交回执，检查原回执先于已被撤销的旧身份；同键改目标返回 identity_conflict，旧 delivery 的处置返回 stale_processing。目标拒绝、无权限或已经终止时保持来源原责任，不执行部分转交。目标还未取得 delivery 时，进程退出由 Runtime 保留转交记录并继续交付。closing 可确认既有输入责任的承接与处置，不能通过交接启动新增业务意图；授权撤回仍按当前范围检查。输入 DTO。

3.5 示例：制作与检查

制作 Work 发布候选版本。检查 Work 须事先完成订阅，才能以 from: "now" 收到本次发布：

await work.events.publish({
  request_key: "candidate:request-7",
  event_type: "card.candidate.v1",
  data: { request_id: "request-7", content_ref: cardV7Ref }
});

检查 Work 登记订阅后，逐项检查候选、发布报告并记录输入处理结果。处理分支退出时，Work 是否关闭由生命周期管理决定：

const sub = await work.events.subscribe({
  request_key: "watch-candidates",
  source: "work-card",
  types: ["card.candidate.v1"],
  from: "now"
});

while (true) {
  const next = await work.inputs.next({ subscription_id: sub.subscription_id });
  if (next.kind === "closed") return;
  const delivery = next.delivery;
  const candidate = decodeCandidate(delivery.input.event.data);
  const reportRef = await review(work, candidate.content_ref);

  const published = await work.events.publish({
    request_key: `review:${delivery.input.id}`,
    event_type: "card.reviewed.v1",
    data: { request_id: candidate.request_id,
      candidate_ref: candidate.content_ref, report_ref: reportRef }
  });
  await work.inputs.complete(delivery, {
    outcome: "handled", result_ref: published.event_ref
  });
}

decodeCandidate 是该事件类型的 schema 校验；review 是通过模型接口完成检查的 Harness 代码。这段程序须运行于持久执行绑定中；普通 async 函数不会自动保存进度。报告的发布键绑定原输入，故障后再次提交返回同一报告。

3.6 发布、受理与处理的确认边界

三种回执对应不同阶段：PublicationReceipt 确认发布记录已保存；InputReceipt 确认目标 Work 已保存输入并承担处理责任；DispositionReceipt 确认 Harness 已记录处理结果。

传输确认和业务处理分别确认：移交给目标 Work 的责任成立后，传输侧才可以确认这次交付；业务处置仍由 inputs.complete 记录。具体事件服务、传输 ACK 和持久输入之间怎样接合，见事件与输入的实现。

暂时不可用或过载时，保留待交付记录并限制新请求；永久拒绝时保存原消息和原因。部署须明确容量、历史范围与清理条件。未完成事项依赖的唯一内容必须保留，否则无法继续承诺恢复。

进程内 pre-request／pre-tool 等 Hook 不属于这套订阅协议。Hook 的改写、拒绝、顺序和清理由Harness 组合契约定义。
