# Installation and everyday use

The user installs independently deployed Runtime, model worker and bundled Harness together without manually wiring paths or Python environments. Source installation requires Unix, Go 1.24+, Node 24/npm, Git and Python 3.10+ with venv support; Python is used by the installer and bundled Harness, whose environment is installed automatically. The installer works outside the checkout, accepts an explicit prefix and atomically activates a complete release. Installation never writes user credentials or replaces host service configuration. Failed upgrades leave the preceding release usable. Sandbox remains a separately operated HTTP service.

`loom setup` selects a native model from Pi's own catalog (or an explicit custom model file), and a remote Sandbox endpoint. It writes a host service configuration and a portable default Work declaration. Reusable defaults are copied into each new Work; existing Work semantics never change when the defaults change. Service credentials are named environment variables or restricted external files, never arguments, Work files, prompts or task environments. Interactive secret entry is hidden; unattended setup requires explicit credential references. Existing output files are refused rather than silently replaced. Installed setup records the deployed `loom-model` command. Each main launcher places its own release's `bin` directory first in its child's PATH, and that release's `loom-model` launches its fixed Node/Pi worker. Upgrading changes the worker used by new invocations without editing configuration, while an already started launcher retains its own release even when `current` changes. Explicit operator-provided worker argv remains supported; source developer setup records its explicit source worker path. Setup performs no provider calls and does not create a Sandbox.

`loom new PATH --userspace DIRECTORY` creates/registers a Work, copies the selected Harness's declared initial Surface content and grants the explicit external task directory. It validates dependencies before creation where possible, never overwrites existing Work/task files and reports a partially created Work if a later grant fails. Optional Harness/definition flags retain external component choice. The Harness manifest's optional `initial_surface` is a relative real directory inside the fixed Harness; it initializes ordinary Surface files before the initial Git snapshot.

`loom ask [PATH] TEXT --request-id ID` is a thin user-facing composition of durable admission and bounded execution. PATH defaults to the current directory. A request ID may be generated and must be exposed before execution, so failed command retries can preserve identity. Identical completed requests cause no new provider call; a pending request may continue only through existing ownership rules. New input admitted during a running/paused Round remains pending and is explicitly reported as queued, not completed. The command displays the final native assistant text; it never marks application success from text or hides unknown outcomes. The advanced JSON admission and inspection commands remain available. Run/resume/status/events also accept the current directory by default.

Acceptance exercises a real isolated install prefix, paths containing spaces, execution outside the checkout, repeat/failed installation, explicit named service configuration, secrets, seeded Surface files, natural-language admission, actual Pi request counts, remote file effects and repeat/no-replay behavior. Missing services fail without host execution. Test output stays outside source. Installation and CLI convenience do not add a daemon, scheduler, model loop or Sandbox implementation.

When the durable controller confirms a Round was rejected before any model/tool dispatch, a worker failure is reported as a local pre-dispatch failure with pending input. It must not falsely suggest an unknown external effect or expose arbitrary worker error payloads. Failure after dispatch retains the existing custody and unknown-outcome rules.
