C / PURPOSE & SYSTEM CONTRACT

01. 为什么需要这个底座

让 Harness 能够按工作需要灵活编写、修改和扩展，而不必反复建设运行基础。

Loom 是一个支持多样 Harness 的中立、持久、可恢复运行底座。 使用者可以用普通代码定义工作如何推进：如何组织上下文、使用工具、处理事件，以及何时继续、等待或与其他 Work 协作。底座提供共同的运行能力，不将工作方式固定为某一种策略或预设流程。

不同 Work 可以使用不同的 Harness，在同一底座上独立推进或按需协作。修改、扩展或替换 Harness，不应要求修改 Runtime 的通用机制，也不应重新建设事件交付、持久化、调度唤醒和执行环境管理。

可恢复是工作持续推进的核心能力。 Work 以文件和持久记录存在；工作资料、策略版本与继续依据不依赖常驻 Agent 进程。需要时加载推进，等待时保存状态并退出，条件满足后恢复继续。Sandbox 是独立执行层，可以本地或远程接入，不决定 Harness 的组织方式或 Work 的寿命。

按工作需要选择和调整 Harness

处理一次代码变更时，Harness 可以按需读取相关实现、修改任务文件并运行验证；持续跟踪某项外部条件时，可以使用另一种 Harness，在收到事件后整理资料、更新判断并决定继续或等待。两项工作复用同一 Runtime 和投影—模型适配结构，不必服从同一推进流程。

每个 Work 独立维护自己的 Surface、策略版本和责任。需要协作时，以明确输入和确定版本的产物交接结果；不需要时独立推进。工作要求变化时，可以调整上下文策略、工具配置或事件处理，在明确的后续推进边界启用确定的新版本，不改变已经发出的请求和既有记录。

Harness 灵活定义工作如何推进；Runtime 提供持久、可恢复、事件驱动的运行基础；Work 可以独立推进，也可以按需协作。

共同结构稳定，策略仍然自由

投影与模型适配是共同运行结构，不是为了自由而取消的约束。 Harness 决定如何从 Surface 和事实形成当次输入、配置哪些工具、如何响应事件，以及继续、等待或协作；模型组件负责 Provider 编解码和活跃模型—工具局部循环。共同边界减少重复建设，不替 Harness 规定具体策略。

不同 Harness 可以共享同一模型组件，也可以复用普通库；不必服从统一业务流程、固定 DAG 或预设计划阶段。Runtime 限制的是权限和交接规则，不是策略语言。当前技术基线保持明确，但不能把参考 Harness 的具体投影算法、文件组织或任务拆解方法提升为底座的唯一策略。

Harness 的 Git 分支、worktree 和合并由上层工具管理，服务于不同工作需要的具体策略及其演进。Runtime 只绑定实际执行的确定版本，不解释分支继承，也不要求建立任意可组合的插件系统。相关边界见第 4 章。

在这套基础上，使用者既可以持续处理实际任务，也可以试验、比较和演进新的 Harness。策略实验是灵活性支持的一种用途，不是每项工作都必须经历的流程。

持久工作，临时执行

Surface 是本 Work 的长期推理面；Userspace 是独立存在的项目代码、数据和产物，可被多个 Work 使用。Work 保存所用资源版本、自己的变更与继续依据，Runtime 的账本和原始记录保存输入、效果与未结责任。文件优先不等于项目归 Work 所有，也不等于只保存 Markdown；继续所需状态不能只留在内存里。

在正常交接边界，下一次推进与重启后的恢复复用同一套加载和继续机制；异常退出还需核对旧写入者与未知效果，不追求恢复任意执行栈。必要状态保存后，Work 专属进程、模型连接和活跃资源占用应可归零；共享 Runtime、执行设施和存储可以常驻。可恢复与按需运行是同一运行模型的两个方面。

事件驱动固定的是输入交付、等待与唤醒方式，不要求把 Harness 内部每个普通函数都做成事件。任务 Sandbox 负责执行，不承载唯一的核心记忆，也不定义 Harness 或 Work 的寿命。

范围与判断边界

Loom 不是一套固定 Agent 策略，也不是通用动态插件组合平台。它不在 Runtime 内预设业务计划、父子任务关系或通用完成判断。默认在持久交接后整体重新加载 Harness，不要求在活跃进程内逐项替换或撤销组件。 同一 Work 更换版本仍须处理状态兼容和未结责任；具体 Harness 可以使用内部插件或生命周期库，但这不是其他 Harness 的接入前提。

Harness 的灵活性是核心目标；不同 Harness 共存与 Work 独立推进是基本能力，多 Work 协作是可选的推进方式。 Work 可以彼此无关；协作也可以使用同一种 Harness。不要求每个任务拆分，不以团队、角色或工作流图重新组织底座。协作契约见第 8.4 节。

首期必须验证普通代码策略可编写、修改和替换，不同 Harness 可在同一底座推进；同时验证文件化工作状态、事件唤醒、卸载与恢复，并复用共同投影和模型适配。任务执行采用既定 OpenSandbox/Linux 基线，验证同 Work 双 Linux 目标；macOS、Simulator、真机和媒体流按实际需要接入，不能用扩充平台数量代替核心验收。

隔离、效果托管、持久提交与完整记录，是使上述能力可靠成立的保障，详见后续契约。本书不承诺任意进程快照、未知效果自动重放或跨宿主共享 SQLite，也不自建第二套模型循环。具体技术选型见第 5 章；重建和发布规则见第 11 章。

任务执行契约与依赖方向

Runtime 核心只依赖 Loom 拥有的任务执行契约，不依赖某个 Sandbox SDK 的类型、异常或状态枚举。厂商 SDK、管理地址、凭据和原生状态映射集中在受控适配器。该边界是代码与语义边界，不要求新建一个常驻微服务，也不要求重新发明远程执行协议。

OpenSandbox 是本版默认且必须交付的任务 Provider 实现；宿主配置绑定其服务与资源池，通用接口不使用厂商类型。新增后端须按第 11 章变更规则接入，不由重建者另选默认底座。只有满足已声明能力、授权、内容交接和责任语义的后端才可替换；统一接口不承诺操作系统命令兼容、活跃进程迁移或未知效果跨 Provider 重试。

资源授权与控制角色

同一 Work 的资源授权上限，不等于所有进程具有相同的有效权限。 Harness 可请求投影提交、获准效果、订阅与等待；启用受限 Work 创建或交付能力时，也只可在授予的范围内请求。Work Bash 不持有该策略控制通道。两者都不能扩大宿主授予 Work 的资源范围，也不能直接改写账本、认领别的 Work、任意设置消费游标或声明某个外部效果已经成功。

控制能力绑定 Work、Round、执行世代、实际策略版本和允许的操作集合，由 Runtime 创建并撤销，不由调用者自报。本版本地协议使用 Runtime 创建的专有继承通道（第 5、6 章）；通道本身不自动证明其不可被复制。Runtime 执行设施负责启动模型可用的 Work Bash，建立不继承控制能力的独立工具角色；不能只依赖 Harness 主动降权。Harness 自行启动的普通子程序仍属于 Harness 策略域，不因为程序名是 Bash 就变成工具域。

Harness 是获得有限委托的策略程序，不是宿主的可信管理员。即使策略错误或恶意，Runtime 仍须验证授权、执行世代、请求绑定和状态转换。Harness 的自述只保存为有来源的策略声明；外部结果与基础设施状态由对应受控适配器记录其实际观察，不把调用者自述升级为 Runtime 已核验的事实。

效果记账以 Runtime 接受的调用为边界。 一次授权 Shell 调用内部的任意 HTTP 请求或业务写入，不自动成为逐项可核对的 Effect。要求更细粒度保证时，必须显式将相关外部访问收敛到受控适配器或出口；不能一面开放任意网络，一面承诺逐项外部效果审计。

Loom 不自建模型厂商编解码、第二套模型循环、版本控制引擎、容器引擎、浏览器或桌面自动化引擎。内部任务执行契约只统一授权、责任与必要操作语义；适配器优先使用已有 SDK 和协议。业务计划、父子任务关系、固定 DAG 和通用业务完成判断不属于 Runtime。

03. 核心对象与状态归属

Harness 是可替换策略，Work 是持久单元；其他对象服务于它们的运行与接续。

Round（推进回合） 一次逻辑受托推进，固定输入边界与策略版本；可跨多个模型轮次、工具调用和恢复后的执行世代。任一时刻只有一个有效策略写入者；Round 不是长事务
执行世代（epoch） 同一 Round 的一次执行所有权标识；用于隔离旧策略请求和内容发布。不是可移植权限，也不能单独阻止远端实际写入
Effect（效果） 可能影响外部系统的调用，含模型请求、执行请求和跨 Work 交付；具有稳定身份、请求绑定及结果状态
Checkpoint（检查点） 关联已确认内容、事实边界、投影、策略与原生继续依据、效果状态的稳定记录；明确可查看范围及可接续条件，不是任意进程或整机快照
原生继续点 模型组件按其协议保存的局部继续状态；单独存在不代表整个 Work 的文件、策略及效果均可恢复
事实视图版本 Runtime 从确定账本边界生成的只读物化快照；供普通文件工具读取，可重建但不具备事实写入权
Profile（环境要求） 版本化的任务能力、平台、隔离、内容与资源约束；Work 可提出要求，不能借此自授设备或网络权限
Target（逻辑执行目标） Work 内具名的任务角色及其要求，例如 default、backend、ios；不等于物理实例 ID
Allocation（资源分配） 某个 Target 一次取得执行资源的绑定，关联 Provider 作用域、原生资源引用、独立绑定代次及回收责任；不同于 Round 的执行世代
Capability（能力） 带版本与限制的受控操作语义；后端声称支持、本次资源实际可用和当前 Work 获准使用分别记录

Work 的推理边界不等于权限边界。 共享资料可按授权读取，当次注意力由 Harness 投影决定；未纳入输入不代表禁止访问。持续维护或长期观察的 Work 可以多次交付而没有一次性终点；参与协作时，才需要明确这次委托的问题、输入和交付约定。

当一部分问题能够凭相对闭合的上下文局部推进、通过清楚的结果接口被消费，并值得独立保存推进、等待和恢复责任时，才适合拆成 Work。仅调整投影、执行计划中的一步、调用另一个模型或切换 Target，不要求新建 Work。独立验证可使用高度重叠的资料，但独立 Work 本身不证明验证正确；交接、冲突处理与最终整合仍需计入拆分成本。

完整事实和已受理责任由 Runtime 账本及不可变记录托管；Surface 与策略代码属于 Work 的版本化文件。Userspace 的资源身份、共享版本和生命周期保持独立，Work 只保存本次使用关系、必要内容及变更的确定引用。 同一资源不因被两个 Work 引用而成为两份“权威项目”；各 Work 账本也不是共享分支当前值的权威来源。需要跨轮保留的上下文选择属于 Surface，选择算法属于 Harness。已保存投影、实际模型输入与来源是历史依据，不作为可丢弃缓存；只读视图、索引和可重建临时产物可重建。Context 不另立目录或状态源。Git 不替代事件账本，数据库不重写版本控制。

Surface 与上下文选择

Surface 保存任务的当前理解，而不要求累积完整的推理流水账；旧版本与原始证据负责追溯。一个 Harness 可以从单个入口文件开始，按需要增加资料或选择文件；不预设 memory/、plans/ 或 context/ 等内部分类。模型的完整内部状态不是 Surface 的保存目标。

选择算法和组织规则属于 Harness。需要跨轮保留、允许模型修改的引用、归档或纳入意图属于 Surface；可由确定版本的 Surface 与策略重新计算的选择不另写一份状态。Surface 表达“后续如何看”，不保存第二套历史或归档事实库。 原始事实仍归 SQLite 账本与不可变记录；实际采用的集合、范围、顺序、正文展开方式及来源随每次投影保存。具体语法归 Harness；第 4.6 节给出随底座交付的最简参考实现，不把其模板格式强加给其他策略。

上下文选择不是访问授权，也不是输入消费游标。移出模型可见范围不等于删除事实、处理输入、取消订阅或结算效果。Harness 验证选择并保持原生工具请求与结果关系；Runtime 提供预算与运行反馈，不决定哪些业务内容应该归档。 默认参考 Harness 由模型主动修改选择；其他策略可显式采用不同方法，但 Runtime 与模型适配层不得暗中截断、摘要或绕过投影记录。

共享只读资料通过确定版本的引用进入 Surface。本 Work 需要独立修改的理解和选择留在私有 Surface 中，不写回共享资料；仅有完全只读 Surface 的 Work 不能宣称支持对其原地修改。不为这一情形重新建立第二个顶层选择状态源。

协作不默认复制其他 Work 的完整历史。发起方明确交付问题与必要引用，接收方将需要保留的理解纳入自己的 Surface；委托关联、交付证据和已采用版本沿用原始记录与检查点。共享资料默认只读，修改使用独立工作副本并按既有内容交接规则整合，不新增协作目录或共享可写事实库。

Harness 版本、投影与引用

私有 Harness 可用普通代码和 Git 演进，在明确的后续推进边界启用新版本；同一 Round 及其恢复不能混用变化前后的策略。Runtime 执行确定的只读策略快照，而不是仅记录版本号后继续从可变源码加载代码。上层管理分支、worktree 与合并。

Harness Git tree：管理具体变体，不增加 Runtime 元模型。

分支和 worktree 用来维护不同工作所需的策略，也支持新策略的试验与比较；Git 合并与代码修改用于形成新的具体实现；普通库和已成熟的扩展边界可以复用，不要求所有能力都能任意组合。不同 Work 可同时绑定不同变体，Runtime 不解释它们的继承、组合或合并关系。

可修改、可验证、可启用是不同的步骤。 使用者或获准的模型用普通代码修改自己的候选 Harness，或按授权修改其他策略项目；在隔离的测试 Work 中检查和试跑，形成确定版本，再明确选择用于后续推进。候选文件保存或 Git 合并成功不代表行为正确，也不自动改变运行版本；检查和试跑失败须可见，不能覆盖既有继续依据。不为此新增插件仓库、候选目录规范或固定编排引擎。

Harness 作者（包括模型）须能在授权范围内读取实际执行的策略版本、与该版本对应的接口和工具 schema、当前获准能力，以及候选检查和试跑结果；这些信息须注明对应版本或读取边界，不能以“最新”资料冒充实际环境。复用普通文件、生成的 schema、CLI 或只读 views/，不新增常驻发现服务；查阅能力不授予调用权限，也不开放共享 Runtime 的管理能力。

默认替换单元是本 Work 的 Harness 执行域。 旧 Round 完成或按第 8 章明确交接后，结束旧执行并在新 Round 加载选定版本；恢复尚未交接的 Round 仍使用原版本。无需重启共享 Runtime，也不得改变其他 Work 的执行版本；不要求每个内部模块提供逆操作。旧执行者须停止或失去实际写能力，远端未结效果仍由 Runtime 按原身份核对，进程结束不等于外部效果被撤销。

源码版本兼容不等于继续状态兼容。更换版本须验证其能读取已有继续状态，否则明确迁移并保留原件与来源，或按历史分叉规则创建新 Work；不能清空责任来“重新开始”。回到旧代码也按新的版本选择处理，不回拨账本或已发生的外部效果。

Projection 是一类有身份的产物，不需要独立的 projection/ 存储。已发布投影、模型实际使用的输入、来源与必要多模态内容必须留存；即使可以重新执行渲染，也不能将历史输入降为缓存。组件将投影转换成不同的原生请求时保留对应关系；相同的不可变内容允许复用引用，而不是无条件重复保存。仍在生成且未被任何已确认记录依赖的临时产物可以重建。

一次投影固定其读取的 Surface、策略、引用及事实边界；后续修改在明确的新投影边界生效，不改变已经发出的请求。检查点通过账本关联文件版本、投影及实际输入、效果和继续依据；不再引用独立的“当前 context 目录”。Harness 的技术继续状态和模型原生继续状态以受控的类型化记录绑定检查点，不要求新增文件目录，也不能用 Surface 笔记冒充任意程序栈恢复。

文件引用可以使用 Markdown fence，语法归 Harness。Work 文件的相对路径按接收 Work 的逻辑根解析；Userspace 内容通过具名绑定与确定内容引用读取，不能隐式假定根下存在 userspace/。保留实际路径或范围、版本与读取内容；缺失、越权、损坏和范围失效明确报告，引用内容默认不作为模板或脚本递归执行。

允许引用自身受控文件、授权的跨 Work 只读内容及已持久化的 Userspace。模板不能隐式穿透网络读取活跃任务资源的内部文件。 远端内容通过显式工具或文件交接，保存为有来源、版本与结果状态的观测后进入投影；已经持久化的授权内容不要求重复远端读取。

事实文件视图

只读视图可以是普通文件，也可以是供标准 sqlite3 查询的派生数据库；“文件优先”不要求每个事实再生成一份 Markdown。最简参考 Harness 的读取面见第 4.7 节。派生格式不改变 state.sqlite 与原始记录的权威归属，也不开放控制表写权。

views/ 采用可重建的只读物化快照，不要求 FUSE，也不要求每条事件提交都同步重写整套文件。每个视图版本从确定账本快照生成，携带来源水位、格式与授权范围，完整发布后不原地修改。

一次投影或依赖一致事实的读取必须固定视图版本，并核验其覆盖本次要求的输入边界；不满足时刷新或明确未就绪，不能把缓存缺失解释成事件不存在。Round 内允许在明确边界切换版本。默认直接使用固定版本路径或等价的受控绑定，不要求提供 current 指针；若实现提供便利指针，也不能依赖多次经该指针读取获得跨文件一致性。

视图刷新不参与事实提交事务，失败不回滚已确认事实；恢复可从账本和记录重建。删除视图缓存不得丢失已记录输入或责任；已被模型实际使用的输入及必要来源另按不可变记录留存。视图保留、活跃读者与授权撤销须协调，不能借旧缓存绕过撤销。物化可以增量和分页，性能要求由实测负载确定。

必要状态不等于必须新建目录

资源声明属于可移植配置，实际使用的确定内容与范围绑定记录或检查点。必要文件依赖可复用受控 Git 内容库保存获准快照，非文件原生产物复用不可变记录；外部存储提供可验证保留保证时也可保留引用。保存必要快照不等于接管整个 Userspace。 不要求每次复制完整项目，但必须保留继续所需字节与语义，不能只留下可能失效的路径、分支名或 URL；导出按第 8.6 节验证依赖完整性。

接收、校验和发布候选是必要步骤，暂存目录名由实现决定，不成为独立权威状态源。未发布不等于可任意删除：被未结责任、活跃传输或提交过程依赖的对象必须有持久记录和保留保护。只能清理确认无必要引用的临时副本；任何必要结果的唯一副本都不得仅以“缓存”或“暂存”名义保存。

展开与事实集合只解释主模板的这两类 fence，不执行 Shell、任意 SQL、循环或递归模板。事实选择针对原生消息可表达的输入、回复及工具交互，不把投影记录和 Runtime 控制事件递归送入自身。开放范围固定到本次合法读取水位；所选集合按已认领输入与完整原生交互的推进顺序去重。账本受理顺序始终保留：推进期间新受理的输入不能插入尚未闭合的工具请求与结果之间；在明确采用边界纳入，投影保存实际采用顺序与原事实身份，不改写账本。
定位与验证投影来源清单标明源文件、块或段落、行范围、确定内容版本与占用估计。展开内容给出简短来源入口；模型按需读源文件后局部编辑，不重复注入整份源模板。必要消息闭包与不可切分边界由代码解析并报告。

本参考语法随 Harness 版本绑定，Runtime 不解析 fence。其他 Harness 可替换语法或选择算法；无需更改 work.toml 的公共字段。引用缺失、越权、范围失效或不支持的媒体形式必须明确失败；不隐式读取活跃 Sandbox 文件。

正文折叠与完整交互归档，是两种动作

动作后续输入如何变化不能改变什么
正文转引用模型将旧工具结果加入 body_refs；保留调用及结果身份、工具/动作、已观测状态和可读原文引用，省去大段正文。只作用于已选集合，不隐式把已归档内容带回。完整原始结果、失败或未知状态、必要错误信息与调用关系均保留。无法安全修改的原生块不支持这种折叠。
交互归档模型将 after 移至一个可归档边界，较早的完整交互不再自动带入。重要约束、当前判断与继续事项应已明确留在 Surface 或获准资料中。不移动或删除事实，不改变输入消费、授权、效果结果和未结责任；不要求先生成全量摘要。
查回或持续引入一次核查用 SQL/文件工具读取原文，作为带来源的历史材料进入当前工具结果。确需持续引入时，调整 after 或 include。不重放旧工具，不将旧请求当新指令，不把检索摘要当原文；重新读取仍受当前授权约束。

先判断是否只需减少展开程度，再判断是否需要移出整段交互。 大段日志与用户的细小约束不能仅因同样“很旧”而一并处理；模型应保留当前有效的要求、更正与未决事项。此处是参考策略的行为要求，不能由 Runtime 凭业务含义自动筛选。

归档边界不能切断原生请求与结果，include 必须带上其所需的完整交互关系；当前必须处理的输入、尚未闭合的工具链及不可省略的继续依据受到保护。代码返回合法边界与保留原因，不让模型手工修复协议。签名推理块等要求原样保留的内容不得改写；不支持的控制明确报告，不能伪造原生消息。

Runtime 提醒，模型决策；超限时明确停止

Runtime／受控模型接入层在请求前报告有效窗口、下一次输入估计、已预留输出与整理空间、主要占用来源、当前保护范围和修改入口；响应后的实际 usage 与下一次估计分开。预算反馈使用已有记录与模型通道，语义见第 6.9 节。不得仅凭上一轮 token 用量假装精确知道下一轮容量。

在还有空间处理一次编辑及反馈时提前提示；阈值、余量、工具可见输出范围和多模态估计方法随参考策略及发布锁记录，不固定一个适用于所有模型的百分比。很大的新工具结果先完整落原始记录，按预先声明的有界输出协议返回范围/分页与原文入口；这是可见的工具呈现契约，不是静默截断、摘要或自动归档。

模型忽略提示、必需输入过大或没有安全可减少内容时，保存现状并明确阻塞，不偷偷换自动裁剪，也不重试未知效果。保留充足整理空间是可用性目标，不承诺任意超长输入均能自主救回。缓存命中不降低窗口占用；稳定前缀与序列化用于减少不必要的缓存失效，不优先于正确的内容更新。[S13]

编辑即表达选择，校验后才生效

模型使用现有文件编辑、patch 或通用 Bash 修改模板；自然语言宣称“已归档”不构成状态变更。后续每次模型调用前，在安全请求边界重建并验证投影；修改生效不必等 Round 结束，但已发出请求保持原样。编辑成功、投影有效、模型已使用分别可观察。

验证失败返回文件/块位置、具体原因及可选合法范围；候选文件不被偷偷回滚，最后有效投影与来源保留。仅当旧投影仍获准、可以保留当前必需输入并容纳诊断时，才在明确标记的修复推进中交给模型改正；修复期间不派发业务副作用。否则阻塞并报告，不悄悄用旧内容继续业务。

不要求每轮重写 Surface，不增加 archive → recall → pin 的必经操作链。反复需要长脚本完成简单编辑、记录定位或边界检查时，才加薄 CLI；它只操作同一份 Surface 或读取现有记录，不持有管理凭据、不另存可见性状态。是否增加封装由实际任务验收决定，而不是以工具数量最少为唯一标准。

模型需要记住的操作方式

当前工作看主模板；资料和产物在已授权的资源目录；旧正文可转引用，结束的交互可归档；要核实时查事实原文。保留当前有效要求与未决事项即可，不写完整思考流水账，也不操作账本、epoch 或恢复游标。

5.1 SQLite 不是“随便使用默认参数”

本版每 Work 通过受控写入入口串行提交短写事务。打开连接时设置并读回以下值；失败则拒绝受理，而不是继续以弱配置运行。busy_timeout、读连接数量和 WAL 清理批次属于实现调优，不能改变幂等与完成语义。

CONTRACT / EXAMPLE
PRAGMA journal_mode = WAL;
PRAGMA synchronous = FULL;
PRAGMA foreign_keys = ON;

权威账本只位于通过耐久验证的本地文件系统；多个 Runtime 实例按 Work 分片，不跨宿主并发打开同一 WAL 文件。SQLite 的 WAL checkpoint 是数据库维护操作，不等于 Loom 的 Work Checkpoint。SQLite 文档明确 WAL 的同宿主约束，并区分 FULL 与 NORMAL 的掉电耐久行为。[S1]

本版要求实际链接的 SQLite 引擎包含官方 WAL-reset 修复：3.51.3 或后续包含该修复的版本，或经确认的修复回移版本。官方也列出 3.44.6 与 3.50.7 回移版本；这不是声称 3.51.3 是最新版本。驱动版本与嵌入引擎版本必须分别记录，不能只锁 Go 驱动模块而忽略底层 SQLite。[S2]

单 Work 同一时刻只有一个有效策略写入者，不等于 Runtime 不能继续受理新输入、保存迟到结果或管理独立清理责任。恢复协调器与策略 owner 分开；新 owner 必须取得实际隔离证据。

5.2 文件、Git 与数据库的唯一提交路线

记录以原始字节计算 SHA-256，临时写入后完成校验和耐久确认，再发布不可变名称；保存必要目录项。Git 以受控参数捕获真实字节：隔离系统/用户 Git 配置，禁止工作树 hooks、clean/smudge 和换行转换改变版本内容，不能因 .gitignore 漏掉声明范围内的必要文件。Git 的 hash-object --no-filters 提供绕过属性过滤的原始对象写入方式。[S3]

本版 Git 配置基线为 core.fsync=all、core.fsyncMethod=fsync；未支持这些设置的版本不能仅忽略警告后继续。持久对象先通过 Runtime 管理的保留引用保护，再提交 SQLite 权威引用；禁止未经协调的自动 GC/maintenance 删除候选或未结责任所需内容。具体捕获可以使用 Git plumbing，不能用一条 git add . 代替范围与字节保证。[S4]

普通文件的 fsync 不自动使父目录项耐久；本版发布流程同时处理必要的文件、目录与底层存储确认。无论 Git、SDK 或文件 API 返回何种成功，最终保证只覆盖验收过的故障模型。[S5]

内容物理分片和压缩算法可以调整；上述原始字节捕获仅针对底座内容库，不改变 Userspace 业务仓库的配置、提交或分支。默认支持普通文件、目录与符号链接，保留字节、相对路径、链接目标及可执行语义，链接不被隐式解引用为授权。空目录或 Git 未表达的必要元数据由版本清单补充。ACL、扩展属性、大小写冲突、设备文件、活跃数据库等需显式能力；必要语义不支持时拒绝捕获或导入，不静默丢弃。UID 与宿主授权不随内容复制。

5.3 本地控制通道与受限进程

Runtime 创建双向字节通道并仅向该次 Harness 进程注入端点；本版约定由启动器暴露为 FD 3。Wire 使用 UTF-8、每行一个完整 JSON-RPC 2.0 对象，字符串内部换行必须转义；不使用 batch。stdout/stderr 是日志而非控制协议。握手帧上限为 64 KiB；后续最大帧大小由双方能力与宿主上限取较小值。超限拒绝，不截断；大载荷通过受控文件发布或分块传输形成不可变记录后使用引用，不能通过放大控制帧绕过资源限制。

同宿主的受信模型适配器可协商 record.file/1：Runtime 在该角色的握手会话中绑定私有记录目录，正文按摘要、字节长度和媒体类型引用；双方校验字节，采用不可覆盖的原子发布。目录位置是本次宿主通道配置，不进入便携 Work 配置，也不授予外部事实确认权。凭据和私有模型传输头仍只在受信控制通道传递，不能进入正文记录。此能力不开放给 Harness 或模型可用的 Bash；Harness 仅向其获准输出目录写候选，由 Runtime 发布，原生轮次通过已有只读来源视图交给策略。跨宿主传输可采用受控对象读写或分块接口，保持同样的引用、校验与确认语义。

首消息是版本握手，失败后不得接受任何状态变更。Work、Round、epoch、策略版本与允许操作集合由 Runtime 绑定通道；消息中的同名字段只能用于交叉检查，不产生身份或权限。Work Bash 由独立执行设施启动，不继承 FD 3 或策略进程访问能力；Harness 子程序继承到的能力仍受同一委托限制。

隔离基线固定 每 Work/角色的独立有效 UID、受限文件挂载视图、进程访问隔离、显式网络策略、无宿主管理 capabilities、cgroup v2 资源与子进程清理。启动设施如 systemd 或等价成熟 launcher 是部署依赖，具体实现必须记录，且不能把单个配置开关当安全证明。命令开始前完成边界建立；范围内的必要写入者未停止或失去写能力时，拒绝冲突接管。[S6]

5.4 模型组件：固定 Pi，但只复用需要的部分

投影、事实选择、正文折叠与预算提示的职责分开：Harness 生成输入内容，Runtime／受控接入层提供预算事实与验证反馈，pi-ai 处理模型 API，agent-core 提供局部循环。参考 Harness 在每个安全的请求边界应用模型已保存的模板选择；不能让 Pi 的 coding-agent 自动 compaction 成为未经声明的第二套上下文策略。参考实现与对照测试分别见第 4.6 节、第 10.3 节。

本版选择 Pi 的模型 API 与 agent-core 局部循环，在受控 TypeScript/Node 组件内适配；不把其完整交互 CLI、默认 Shell、扩展装载、自动上下文压缩或独立持久调度接入 Runtime。组件持有获准的模型服务连接，不向 Harness 或 Work Bash 传递管理凭据。

Pi 文档提供自定义模型调用函数、工具钩子和继续入口，但“能订阅事件”不等于“事件处理会阻塞下一次效果”。因此，本版要求使用所锁定版本中可等待确认的屏障：发送每次模型请求前、执行每次工具前、继续依赖结果前，均等待 Runtime 持久确认；不能仅在事后监听事件写日志。[S7]

默认工具顺序执行；并行仅在 Runtime 已确认独立资源、明确效果身份和无冲突后启用。模型状态保存与继续阶段按版本报告并验证；continue() 只能推进既有状态，不能自动重试结果未知的请求。需要补充适配 hook 时在适配层实现并锁定；无法建立必要屏障就不宣称该版本已符合本书，不另写第二套模型循环弥补。

5.5 OpenSandbox 的默认实现

本版 Go 适配器调用官方 Go SDK，参考验证部署使用 OpenSandbox 的 Linux/Docker 后端。服务端、SDK、执行镜像各自锁定版本或摘要；管理端点只存在宿主配置中。官方仓库已提供 Go SDK，并把 Sandbox 生命周期与执行 API 分开。[S8]

关闭会导致未知外部效果重放的 SDK 自动重试；只读查询和按同一身份确认幂等的传输可以重试。服务端支持某操作不等于提供 Loom 的所有耐久与恢复保证；适配器仍须补齐第 7、8 章的原目的地绑定、结果留存与交接确认。

5.6 版本固定的三个尺度

规范版本确定行为和公共字段；基线版本确定上表组件与路线；发布锁确定源码 commit、编译器/运行时、直接与传递依赖、嵌入引擎、协议、镜像摘要和测试环境。常规补丁升级不必改写产品目标，但必须产生新发布锁并重跑受影响测试。

本书不编造尚未生成的 lockfile 或“已测试版本组合”。首个实现发布必须提供完整锁定与兼容矩阵才可声明可复现构建；重建者不能用 latest、漂移标签或只记录“Go + Pi”充当发布身份。模型服务实际 ID、语义参数与可用版本逐请求留存，不承诺云端模型输出逐字节可重复。

6.3 Effect 的固定语义

dispatch_state 与 resolution 分开；取消、文件交接和资源回收继续独立记录。原生返回业务错误也是“收到原生结果”，不能据此推导所有副作用未发生。

字段 允许值 含义
dispatch_state prepared / attempted prepared 尚未发放派发许可；attempted 在可能调用远端前持久记录，不保证远端已收到
resolution unresolved / native_result / confirmed_not_executed 不确定保持 unresolved；终止运行的证据不等于 confirmed_not_executed
observation pending / running / unknown，及来源记录 是当前知识状态而非授权；超时转 unknown 不重置派发状态
cancellation none / requested / stop_confirmed / unknown 停止确认只证明声明范围内不再继续，不撤销已经发生的副作用
content_deliverynot_required / pending / confirmed / failed / unknown确认本次必要内容已持久保存；不表示业务验收通过或已经合入共享目标

派发协调器先以条件更新把 prepared 变为 attempted，持久化后才调用适配器；竞争者不得再发放同一次许可。崩溃发生在写 attempted 之后、远端调用之前，也保守核对，不能因为“很可能没执行”而重新发出。恢复只能安全派发仍是 prepared 且原执行者已被隔离的请求。

confirmed_not_executed 只能来自可验证的未接受/未执行证据，不是错误字符串推断。再次执行须建立明确的新效果或经原生幂等契约核对原请求，保留关系；本版不自动重试非幂等模型或工具效果。手工请求新尝试也不能改写旧未知效果。

Round 的状态至少区分 ready、running、recovering、blocked、handed_off。崩溃转 recovering/blocked；handed_off 表示剩余责任已被明确接管，不表示业务完成、效果都成功或所有资源已归还。

使用 Userspace 的策略、执行适配器通过 session.hello 声明 userspace.binding/1。该能力给既有记录与 destination_binding 增加 userspace_bindings_ref，不新增 RPC 或常驻资源服务；未协商时不得运行依赖此绑定的操作，不涉及 Userspace 的操作不受影响。

清单是 schema_version = 1 的不可变记录，包含 bindings 数组。每项固定 alias、宿主作用域内稳定的 resource_scope 与 resource_id、working_copy_id、实际获准的 access、授权内容范围清单 scope_ref（record_ref），以及 base_ref（本次副本所依据的确定 content_ref 或不可变快照 record_ref）。read 的工作副本可以是只读内容视图；设备只消费产物时可直接绑定产物引用。

Runtime 在效果下发前核验清单与现有 Work、Target、Allocation、epoch 的对应关系；相关副本版本变化时生成新清单，不修改旧绑定。base_ref 是该副本本次操作的基线，不是共享项目的“最新版本”。 保存结果以原绑定、原副本前序及新内容引用关联；资源重绑、迁移或重建后，历史效果仍按原身份核对。可移植记录保留来源和确定内容，读取授权与物理挂载在新宿主重新建立。

6.7 兼容性边界

公共配置、协议对象、导出格式及本书明确给出的读取格式按版本兼容；SQLite 内部表和 Go 内部类型不是跨进程 ABI。第 4.7 节参考读取结构与第 6.9 节反馈各自版本化，不等于公开控制数据库布局。兼容新增可选字段需要默认值、旧端行为和测试；新增必需能力须协商，不认识时失败关闭。其他 Harness 无需采用参考模板语法，其解析规则与实际 Harness 版本绑定。

默认支持当前格式；声称能导入旧格式时必须提供该范围的迁移与验证。迁移在稳定边界保留原件和来源，不能原地改写不可变原生记录。未知效果仍在旧适配器和原目的地上核对，不能靠升级 Provider 或协议把责任清零。

从配置结构 1 升级到 2 属于显式迁移。 旧 [userspace].path 和 Work 内任务目录不得自动解释为新的资源授权。迁移先固定旧内容及未提交变更，明确独立资源身份、工作副本和访问范围，再生成新配置与绑定；保留旧版本、原效果目的地和必要字节。不要求物理移动项目，但默认导出不再递归接管该目录；依赖捕获未完成前不能删除旧数据。未实现该迁移时明确拒绝加载旧格式，不静默接受或复制路径作为身份。loom/1 外层协议与已有记录不因此改写。

授权、交付身份与取消

创建授权单独授予，宿主核验目标配置、可读输入和实际能力，并绑定允许的预算、并发与资源额度范围。新 Work 不继承调用方控制通道、宿主权限或未决效果重放权；创建不能重置共享额度。上限耗尽或授权不足时拒绝新增责任，不抹掉已受理责任。申请要求不是授权，授权绑定不随 Work 导出。

定向交付固定目标 Work；来源由通道确定，不能伪造。源事件身份由 Runtime 持久绑定到 Effect；同一事件经直接递送或订阅补交时复用同一目标受理身份。回执丢失只能按原身份、原内容、原目标核对或重投，不另生成一次业务交付。

effect.cancel 只登记原创建或交付操作的取消请求，不能删除已创建 Work、收回已受理输入或推导它们已停止。业务委托撤销通过关联事件传达，由 Harness 处理；强制停止执行须另经获准的停止或撤权路径并取得证据，不从“父子关系”推导级联取消。

在窗口内的压力请求允许模型继续或编辑；超出硬限制的请求不发送，保存可修复状态与原因。已发送请求遭 Provider 拒绝时记录真实错误，未得到明确结果时保持未知，不一概当作未执行后重试。工具呈现范围和任何对照策略的压缩决定都经 Harness 明示，并与完整原始记录区分。

C / SYSTEM CONTRACT

07. 执行目标与内容交接

Userspace 是独立任务资源；工作副本供执行使用；Target 与 Allocation 决定在哪里执行。

Work 执行域

同一部署默认复用一套 Linux Work 环境及实际文件系统。增加 Work 不要求增加容器或虚拟机，活跃时启动受限进程，等待时释放专属进程。macOS 宿主通过成熟 Linux 运行设施提供此环境，不假定 macOS 原生具备 Linux 隔离机制。

复用 Unix 身份、ACL、受限文件视图及进程/网络隔离设施；对 Harness 与模型可用的 Work Bash 建立可验证的角色隔离，而不只按 Work 共享身份。本版使用分离的角色 UID 并组合进程与文件隔离；具体启动设施按第 5 章锁定和验证。工具角色必须不能取得策略控制通道、读写策略进程内存或替换正在执行的策略快照。

ACL、软链、私有路径名或单一 FD 都不能独自证明完整隔离。继承 FD、进程调试与 FD 复制、管理端点、父目录替换和残留子进程必须纳入负向测试。网络按显式能力授权，Work 不默认获得任意外联或 Sandbox 管理权限。共享环境具有共同故障域，CPU、内存和进程限制由成熟资源设施执行。

任务执行域

任务执行面不限定为 Linux 容器。Sandbox 在本文中表示受控的任务执行域，可以由容器、虚拟机、专用机器或受控设备会话承载；这些实现不具有相同的隔离强度，也不要求暴露相同的功能。平台、CPU 架构、Shell、工具链、设备与图形能力均按明确要求核验。取得物理设备使用权不自动证明已获得安全沙箱。

网络、设备和权限由 Work 要求与宿主授权共同决定。只在可证明隔离的配置下提供任务域 root 或安装能力，不得因此获得承载该域的管理权限、Work 控制目录、其他任务资源或 Provider 凭据；对于不能提供同等隔离的后端，必须拒绝不满足其信任要求的工作负载。

活跃推进可以复用获准任务实例，不要求每条命令新建 Sandbox。Userspace 独立于 Work 和 Sandbox；属于 Work 继续状态的是资源使用绑定、确定内容引用及其已保存变更，而不是共享项目的所有权。 资源可以位于获准的本地或远端持久存储，内容确认不要求回传到 Runtime 主机。文件目标只获得与原资源、工作副本、Work、Target、Allocation、epoch 和范围绑定的内容；无通用文件系统的设备仅接收获准产物与操作。

Target、资源分配与能力

一个 Work 可以有零个或多个具名 Target。Target 是逻辑角色，Profile 表达要求，宿主配置把获准要求解析到 Provider 和资源池，Allocation 记录某一次实际分配。Profile 引用必须解析成可追溯的要求快照；同名 Profile 后续变化不得改写已有分配的历史。

同一个 Provider 可以分配多个目标，多个 Profile 也不要求多个 Provider。后端内部的容器、VM、构建宿主、模拟器或设备池可以组合，但 Runtime 必须得到足以确定真实执行目的地的资源身份；不能让一次设备操作依赖后端隐含的“当前设备”。

任务执行契约保持小型公共核心：取得资源、查询原有申请或分配、归还使用权、报告能力与原生结果。Exec、文件交接、屏幕捕获、UI 输入、浏览器或设备控制、媒体流和服务连接属于可选、版本化能力；不能要求每个 Provider 都实现全部方法，也不能把不支持伪装为空成功。每个被使用的能力仍须满足原有 Effect 身份与未知状态规则。

后端支持、本次可用和 Work 获准，是三个独立条件。 初始化成功不替代设备、工具链或权限核验。Runtime 将实际平台、能力、限制与就绪依据发布为只读事实供 Harness 选择工具；模型仍需知道 Linux 与 macOS 的命令、路径和设备差异，统一契约不隐藏这些任务语义。真实设备目标可以没有 Bash；Bash 只是具有对应 Shell 能力时的工具入口。

路由、绑定与故障核对

工具元数据区分 Work 域与任务域，并在任务域指定逻辑 Target，例如 bash(environment="sandbox", target="backend", …)。缺省只解析到 Work 明确声明的 default，不选择“第一个可用实例”。缺省目标缺失、能力不足、授权不足或未就绪时明确失败；不分析命令猜测路由，不退回 Work 或宿主 Shell。

在工具效果下发前，Runtime 固定并持久绑定 Work、Round epoch、Target、Allocation、目标绑定代次、Provider 作用域及必要子资源。涉及 Userspace 时同时保存资源绑定清单，不能仅凭当前目录名确定读写对象。模型通常选择 Target 与逻辑资源，其余身份由 Runtime 注入并核验。Target 重建与副本重建分别留下新的绑定，不改写旧请求目的地。

尚未取得原生资源 ID 的申请，先绑定已选择的 Provider 作用域和稳定申请身份，收到原生引用后追加关联。申请超时不等于没有创建资源；适配器只能按已验证的原生能力核对，无法确定时保留未知与清理责任，不盲目重复分配。

重连、查询、取消、文件交接及迟到结果核对都使用原绑定，不重新解析 Target 的当前指向。原目的地已经消失时记录丢失或未知，不能把旧效果发往同名新实例。旧资源释放与新资源取得分别留存；尚未隔离的旧写入能力继续阻塞对同一受保护目标的冲突操作。

Userspace、工作副本与共享内容整合

Work 是工作实例，Userspace 是被处理的资源，工作副本是本次读写视图。 多个 Work 面向同一项目是正常用法，不是“外部 Userspace”特例；各自保存进度不需要先取得整个项目的独占权。独立项目可沿用自己的仓库、分支和发布流程，Loom 不另造版本控制器。

本版采用独立工作副本＋显式文件交接；Git 项目可沿用分支、worktree 或独立 clone，数据任务采用等价的隔离副本。它们是内容组织方式，不单独构成权限隔离。默认不允许任意共享可写树；直接共享写入只在额外声明并验证无重叠范围或可靠协调、且宿主明确授权时开放。排他约束针对实际冲突范围，不把整个 Userspace 锁给一个 Work。 无论副本机制为何，任务进程都不得因此获得可修改其他副本或共享分支的仓库控制路径；权限校验不能只检查业务文件树。

文件交接须固定写入范围并捕获真实字节；exit 0 是执行观测，不等于必要内容已保存。完整 Work 检查点还需满足策略与模型继续条件。持久卷同样需要稳定捕获与确认，后台进程、内存缓冲和应用级数据库按实际能力处理，不能仅凭父 Shell 退出判定全部写入结束。

在产物确认前，不开放依赖其已交付结果的后续步骤；显式批处理需预先声明确认粒度和最大未确认损失。同步失败不擦除原生结果，恢复按原 Effect 与交接身份核对已上传内容；只重试有已验证幂等性的传输，不重跑结果未知的命令。缓存不可成为必要状态的唯一载体。

整合到共享目标

合并、冲突解决和是否验收由 Harness、使用者或已有开发流程决定，Runtime 不自动合并业务文件。共享更新复用已有获准工具与 Effect，不新增通用合并引擎；工作副本写权限不包含共享分支、仓库或发布目标的更新权限。需要可核对的更新保证时，写入口必须收敛到支持预期版本校验的受控路径，不能靠分析任意 Shell 命令猜测其发布语义。

两个 Work 的 SQLite 事务不构成共享资源锁。 条件检查必须在真实仓库/存储目标原子执行，或由覆盖全部写入者（含其他 Runtime 与用户工具）的协调保证；不能先读版本再无条件覆盖。后端缺少必要能力时拒绝宣称安全共享更新，已保存候选仍可交付给外部整合流程。

共享更新独立记录原请求、目标、预期版本、候选内容与原生回执；回执丢失保持未知并核对原目标，不用新 key 自动重复发布。当前目标已变化时不能仅凭“不是预期旧值”推断原操作未执行；后端证据不足则继续未知。合并成功也不等于业务验收通过，更不要求为保存 Work 进度先完成整合。

多目标协作与设备观测

同一 Work 可使用多个获准目标，但不因此产生多个策略写入者。各目标可分别保存自己的副本进度，不采用“整个项目只有一个 Work 能发布内容”的规则；更新同一共享目标时才按第 7.5 节协调。跨目标产物交付携带资源与内容来源、目标和分配身份、平台要求及持久确认；不隐式双向同步可写树。

目标之间默认不因同属一个 Work 而网络互通。联调必须声明方向、逻辑服务、端口或等价通道以及接收方授权，由成熟网络或隧道设施实现。动态地址属于宿主解析结果，不作为可移植 Work 配置；绑定改变后原效果仍保留原目的地。只有实际链路与服务能力已核验，才能声明对应联调能力 Ready；未实现连接能力时明确拒绝，不静默开放公网。

GUI、浏览器、模拟器与真机操作可使用已有自动化引擎，由受控适配器接入。屏幕观测必须明确目标、分配、设备或显示面、会话代次、采集时刻、尺寸及内容引用；输入动作必须绑定对应资源与坐标/输入语义，不能靠“当前屏幕”猜测。截图不等于完整设备检查点，点击或安装超时也不授权自动再做一次。

媒体流是会话型数据通道，不把每一帧都变成一条控制账本事件。账本保存会话授权、开始/结束、失败及相关 Effect；模型实际使用的帧、片段或文本转录，按原始输入记录要求持久引用。重连不重放输入动作，断开的实时画面不能充当后续恢复的唯一依据。

归还、清理与底层容量

Allocation 归还只表示该次执行资源的使用权已结束，相关进程、会话、通道及写入能力已按声明范围停止或隔离；不等于撤销全部 Userspace 授权，更不删除 Userspace。 专用副本与资源池残留须在独有变更已保存、未结责任和必要引用已保护后清理。共享机器是否保留、何时销毁、再次出借与计费结束由部署设施分别报告。

等待时应可归零的是 Work 专属的活跃占用，不是所有共享基础设施或云账单。预热池、最短计费周期和取得资源的延迟属于容量与成本约束。成本要求由上层提出、宿主授权与 Provider 事实约束，Runtime 不内置按业务阶段选机器的策略；所有目标分别核对与归还，一个失败目标不能抹去其他目标已经保存的结果。

声明式环境与 Ready

Work 按具名 Target 声明环境要求，并引用 Userspace 中确定版本的环境定义或依赖锁；项目自身不必理解 Work 的 Target 命名。宿主解析获准服务、镜像、工具链与设备，记录实际要求和来源。不同资源的环境要求冲突时明确处理，不静默覆盖。规范解析与构建优先使用成熟设施，Runtime 不另造 devcontainer 解释器。

  1. 校验 Target 要求快照、授权、预算约束、内容版本与必要服务，选定获准的 Provider 绑定。
  2. 保存资源申请身份与责任，再取得资源；在任何用户代码运行前建立并核验资源身份、授权文件或产物绑定、网络及安全隔离上限。
  3. 在已受限的任务域执行适用的初始化，保存输出与原生结果；初始化不能扩大授权，没有 Shell 的目标不以 Shell 初始化为前提。
  4. 按本次请求的能力核验实际平台、依赖、工具/设备通道及必要服务，复核授权与隔离，记录绑定代次及就绪依据后开放对应操作。

初始化脚本 exit 0 只是观测之一，不能单独证明依赖、挂载、桌面、设备或权限满足要求。Ready 绑定具体分配及所需能力，不是后端类型上的永久布尔值。失败或不确定保持对应操作未就绪，已申请资源仍需核对与回收。

08. 推进、等待与恢复

工作持久存在，执行按需发生；正常接续与恢复复用持久加载机制。

停止后再加载，是正常运行方式，不是异常时才附加的补救流程。 Work 的文件、版本、记录和等待责任保存在持久层；事件使它再次具备推进机会。一次活跃推进可以包含多个模型轮次和工具调用，不要求每一步都卸载进程。

输入、推进与提交

Runtime 先持久受理输入并取得排他推进权；Harness 按确定版本生成投影和策略决定；Pi 运行原生模型—工具循环；Runtime 在每个外部调用及结果边界托管责任，工具在获准执行域运行。

每次模型请求都在相应安全边界读取已确认的模板与事实选择，并执行预算反馈和容量校验；候选拒绝与超限阻塞保留既有责任。恢复同时保留模板选择、折叠/归档来源与最后有效输入，不因重启重新生成一份假想历史；查回旧事实不重新执行该事实对应的动作。

Round 是聚合交接边界，不是唯一落盘时机，也不是覆盖整次推进的数据库事务。效果身份和请求在下发前持久保存；已收到的原生结果与继续依据在确认或交接前持久保存，不等 Round 结束。已保存的事实证明“系统记录了什么”，不自动承诺它对应一个完整可接续现场。

检查点与 Round 内接续

可接续检查点必须处于与其捕获范围相匹配的稳定边界：必要文件已形成确定版本；策略可以从显式状态重新进入；模型组件有已验证的原生继续方式；相关效果结果或待核对责任已持久化。稳定边界可以在 Round 内、两次工具或模型操作之间，也可以在 Round 交接时；不要求整个业务已完成或所有资源已释放。

稳定不等于业务正确。未完成的代码、失败的构建结果和明确的待核对效果都可以被忠实记录；不允许的是把持续被修改、捕获撕裂或只存在于内存中的状态宣称为完整可接续检查点。包含未知效果的继续状态，最多授权进入查询、核对或明确阻塞，不授权重新下发同一个未知效果。

进程崩溃不会使原 Round 自动完成或回滚。Runtime 保留其责任，进入待恢复或阻塞状态；在旧执行者对受保护状态的实际写能力已停止或被隔离之后，才能向新的执行世代发放策略推进权。租约到期只是怀疑信号，不能替代该隔离。

旧世代的策略请求和内容发布必须拒绝；原有 Effect 的迟到原生结果仍可经受控适配器按原身份记录和核对。拒绝旧 owner 不等于删除旧效果的事实。策略更换应结束或明确转交原逻辑推进后另开 Round，而不是在恢复中偷偷替换版本。

检查点记录本次继续依赖的 Userspace 身份、各副本确定内容、产物、Allocation 与未结效果，不保存一个全局“当前 Sandbox”或“当前项目版本”。只协调本次捕获所需的写入范围；已经固定的资源快照不要求其他无关 Work 停止。设备、服务数据和目标间消息分别声明可丢弃、可重建或可核对的边界，不虚构跨资源原子快照。

持久提交顺序

交接时先协调本 Work 及相关副本的捕获范围，保存产物、原始记录和必要内容对象，并建立保留保护；再由短 SQLite 事务验证执行世代、本副本预期前序与检查点前序，提交引用。之后可刷新本 Work 的派生指针和视图。此提交不更新 Userspace 的共享分支，不要求各资源的“最新版本”保持不变。 多资源检查点绑定的是实际使用的一组确定版本，不承诺它们来自同一全局时刻。

Git、文件与 SQLite 没有天然的跨系统原子事务。 本顺序允许留下没有被提交引用的候选对象，不允许已提交检查点指向尚未持久化的内容。垃圾回收必须识别数据库引用、未结责任、活跃读者和正在提交的候选，不能由普通 Git GC 提前删除它们；可通过受控保留引用等成熟机制实现。

“已落盘”按声明故障模型验证：涉及主机崩溃或掉电时，不能只检查 write()、Git 命令或 SQLite 默认配置返回成功。实现要验证所用存储的耐久确认、必要目录项持久化以及数据库同步设置。进程崩溃、主机掉电和持久存储介质永久丢失不是同一个保证范围。

检查点的事实水位也不等于输入消费游标。只结算本次明确认领并完成处理的输入责任；Round 执行期间新到的输入仍然待处理，即使它们的事件已经出现在较新的账本快照中。

Harness 决定继续、阶段结束或等待条件。内容提交、Round 责任交接、效果结算和资源释放是分别记录的状态。 必要状态已经持久化、写入已协调且剩余责任已由 Runtime 明确接管时，可以记录 Round 已交接；这不宣称待决效果成功，也不宣称资源已释放。只有释放证据齐备，才能记录资源回收完成。

因此，远端释放回执丢失不应阻止保存已经可靠取得的结果，也不强迫 Harness 常驻等待清理。Runtime 托管后续核对与回收；仍能修改共享目标的旧执行者则继续阻塞冲突性接管。不能把清理失败改写为成功，也不能让一个无关清理任务阻塞整个 Work 的事实受理和历史读取。命令结果、模型停止、预算耗尽、等待输入、业务完成和释放状态分别记录。

事件等待与可选的多 Work 协作

多 Work 协作是 Harness 可选用的推进方式。 Harness 决定拆分、上下文选择、结果接受与后续推进；Runtime 复用授权、创建、持久受理、交付与唤醒机制，不解释协作拓扑或业务完成。不使用协作的 Work 无需额外的角色、配置或状态机。

等待可靠输入，不把业务判断交给 Runtime

Harness 用普通代码定义依赖与继续策略；Runtime 托管获准来源、事件类型和关联引用等机械筛选，以及订阅、历史补齐、去重、游标与唤醒。等待依据是已记录事实，不是“从现在开始监听下一次通知”。检查已有事件与建立订阅的竞态不能丢输入，通知仅是提示。

收到 A、B 的结果是否足够、是否冲突、要不要接受或再委托，均由 Harness 在推进时判断。它保存已采用的交付身份、版本、判断和依据，纳入策略继续状态与检查点；条件未满足则再次交还执行权。业务汇合可以是普通代码或库，不要求 Runtime 提供任意谓词、all_of/any_of 解释器或 DAG 调度。

交接只结算本轮明确处理的输入。若新输入在判定等待后、订阅登记或 round.handoff 期间到达，必须保持待处理并再次触发推进，不能被“进入等待”覆盖。接收方卸载或重启后，仍从持久责任和已记录交付继续。

跨 Work 允许至少一次投递，目标按稳定来源与事件身份原子幂等受理；目标输入持久化后才确认交付或推进对应游标，不假装拥有跨库全局事务。同一事件可按原身份、原内容、原目标补交；重复通知不等于重复输入，更不授权再次运行未知的模型或工具效果。历史保留不得删除未结责任的唯一依据。

显式交付与接受，不默认共享完整历史

交付说明对应哪次委托、哪个输入基线和哪些确定版本的产物；摘要只是读取入口，不替代必要的原始内容与证据。引用不自动授予访问权，跨 Work 读取与接收事件分别授权，读取文件不等于消费输入。接收方需要的内容沿用既有 Retention 保护或保存获准副本，不因来源 Work 结束而丢失恢复依据。

发布产物、业务完成、接受结果是不同判断。 Work 可以多次发布，Harness 的完成声明只按其来源记录；Runtime 确认内容和交付，不替业务验收。接收方针对明确委托及结果版本决定采用、拒绝或继续验证，重复事件不得使同一接受决定无意重复应用。

结果必须与被验证的版本对应。

A 委托 B 验证 V17，随后 A 改为 V18。B 迟到的“通过”仍是关于 V17 的记录，不得自动作为 V18 的验收依据。委托取消或被替代后，旧结果仍保存为事实，是否另行使用由接收方明确决定。

固定与动态，共用交接机制而非工作流表示

Harness 可以预先写明流程，也可以推进时创建或委托 Work，或把二者组合；计划中的一步不必是一个 Work。动态创建使用第 6.8 节的受限入口，不等于复制父 Work 的历史或执行 fork。新独立任务通常创建新 Work，同一任务的补充输入可继续已有 Work；复用 Harness 模板不等于复用任务身份。

计划修改不撤销已创建的 Work、输入或外部效果。取消、替代与重新委托显式记录，停止请求不等于已停止，也不自动级联。各 Work 使用授权只读内容或独立副本；各自保存与共享整合按第 7.5 节分开，接收方负责整合和整体验证。多个局部完成不代表整体正确，引用同一 Userspace 也不强制它们参与同一协作流程。

等待时，任务专属 Harness/Agent/模型进程、长连接及各 Target 活跃占用应可归零；共享 Runtime、执行设施、资源池容量与持久存储可以常驻。归还、清理、物理销毁和计费结束不混为同一事实；结果或归还未知时保留原绑定及责任，不假装已经回收。

历史、继续与 fork

历史操作区分三种语义：查看已记录事实、从已确认继续依据接续同一责任、从历史内容基线创建新 Work。每个已记录事件都可查看其已保存内容，但没有内容快照的事件不承诺还原当时完整文件系统。

同一责任的继续使用最新可用的已确认依据，并核对其后已经发生的效果；不能拿较旧检查点跳过后续责任。精确恢复中间模型/工具阶段依赖实际模型组件的原生能力、已保存策略状态和相关文件版本。缺少条件时明确标为不可在该点接续；允许查看或按既定历史规则分叉，不靠重放猜测过去是否执行过，也不另造模型循环。

发生过外部效果的 Work 不允许抹掉后续历史并就地回拨成“从未发生”。普通文件回退只能作为新的可追溯变更；从历史状态开始另一条尝试使用新 Work 身份与分叉关系、独立可写内容和任务环境。接续最新确认的同一责任与历史 fork 是不同操作。

Fork 继承确定版本的 Surface、策略、必要输入/投影及资源基线引用；继续开发时准备新的可写副本，不复制原 Work 的副本写权、活跃 owner、宿主权限或未决效果重放权。Fork 一个 Work 不等于复制或 fork 整个 Userspace 仓库。 原责任保持存在，迁移同一责任仍须隔离原 owner。

恢复 Work 不回退共享 Userspace。 A 基于 V17 的副本已经保存，项目后来推进到 V20；恢复 A 时重建其保存状态与必要副本，继续用旧基线或显式接纳 V20，不自动 reset、覆盖或同步回共享项目。需要改变共享内容，仍执行独立、获准、可核对的操作。

结束、归档或删除 Work 不级联删除 Userspace、共享分支或其他 Work 的内容。清理专用副本前确认未提交变更已妥善保存，或由有权限的使用者明确放弃；被其他交付、检查点或未结责任引用的内容继续受 Retention 保护。Work 的生命周期操作不是资源所有权操作。

导出、导入与同一责任迁移

导出首先固定 Work 的一致状态及所需副本快照，协调相关策略、写入与账本提交；不需要冻结整个 Userspace 或无关 Work。SQLite 使用已验证备份机制或受控停写快照，纳入已提交 WAL；只复制 state.sqlite 不代表完整数据库。数据库一致性不替代相关文件的稳定捕获。[S11]

导出记录配置/schema、Work 身份、检查点与责任、Git 内容、不可变记录，以及必要资源身份、版本和依赖范围清单。资源只导出已获准的必要内容或具有可验证保留保证的引用，不递归接管整个项目，也不带走其共享分支管理权。摘要与可用性均须验证；无必要内容或保留保证时拒绝声称可完整恢复。派生 views 可重建；凭据、可用 token、宿主权限不导出。历史效果的非秘密原目的地身份保留，迁移后另行授权核对。

导入先验证完整性与路径安全，在无执行权限状态下注册；导入依赖快照不使其成为原 Userspace 的新权威项目。宿主重新绑定资源身份与授权，旧效果不因同名新资源而改目的地。迁移同一 Work 必须证明原 owner 失去实际写能力，否则仅受限查看或按 fork 创建新 Work。继续开发准备独立副本，更新原资源仍需相应授权与并发检查。

介质永久丢失、异地灾难恢复与跨宿主高可用不由本版单机耐久承诺覆盖；需要这些目标时增加明确复制/备份契约与故障测试，不能从 Git 或 SQLite 的存在直接推得。

10.2 性能、证据与通过条件

等待驻留规模、活跃吞吐、事件延迟与长期恢复分别测试；不能把“启动一个 Work 成功”作为系统规模证据。每次性能验收在运行前固定 Work 数量、活跃并发、事件速率、事实/文件体量、持续时间、硬件和阈值；结果注明适用范围。没有声明阈值就不能写“达到目标性能”。本版不捏造尚未测量的吞吐值。

每条验收保存 test_id、规范/基线版本、源码与发布锁摘要、环境、故障位置、预期断言、实际观测引用、结果和时间。状态只能是 pass、fail、not_run、skipped、unsupported；必需能力只有 pass 可计为通过，可选能力 unsupported 必须不向使用者宣称可用。

核心通过判定基于实际数据库、文件字节、原生请求、受控调用次数、进程/FD/网络行为和资源状态。通过结果属于具体发布，不能写回本书变成无条件的产品事实。

方案保持相同的条件要比较的差异
A · 默认参考同一任务输入、模型/参数与预算、初始 Surface、原始记录、检索能力、工具与资源隔离。各自后续产生的真实轨迹仍完整保存。Runtime 报告压力；模型自己修改 Surface、折叠正文或归档，并按需查回。
B · 简单规则对照不因方案变化关闭检索，也不将另一方案生成的摘要或正确答案提前注入。固定并记录规则阈值。只按明确规则将旧工具正文改为引用，保留近期原文与必要关系；没有空间时按已声明停止行为处理，不偷偷加摘要。
C · 摘要对照同样可访问原始记录；摘要调用、延迟、费用与失败计入总成本，摘要保留来源。摘要旧内容并保留近期原文，测试是否改善持续对话与约束保留；不是 Pi/Runtime 的隐式默认功能。

对照是在隔离测试 Work 中执行的不同 Harness 策略，不增加线上自动切换器、通用压缩框架或新的 Runtime 管理机制。可容纳的短任务增加完整历史参照；长任务通过受控窗口和足够多次交互触发多次整理，不能仅降低窗口跑一个成功样本。至少重复运行以显示模型波动，不把一次胜负当结论。

HTML 卡片多轮修改早期“不提某段经历”“未确认不能发送”等限制在多轮检索、工具输出与归档后仍被遵守；产物、预览和对外发布分别确认。

安全与继续私人/群聊资料隔离；折叠结果不隐藏失败或未知；查询不触发旧动作。进程退出后从同一模板选择和持久依据继续，且不回退共享资料。

运行前固定任务集、允许检索范围、关键断言、重复次数、质量门槛和成本口径；可程序判断的行为直接断言，需人工判断的内容预先确定标准并独立复核。先通过关键约束、权限与动作安全，再比较任务完成质量、来源正确性和检索召回；最后比较有效输入量、真实费用、缓存命中、总延迟、纯管理模型调用、无效编辑、SQL 重试与重新读取次数。不得以省 token 换取关键约束失败，也不把缓存命中当窗口缩小。

参考目标是普通短任务不增加纯上下文管理模型调用，长任务只在有需要时编辑、折叠或归档；正常任务必需的查资料与纯管理开销分开计数。没有预先门槛、只看模型自述、未测或跳过均不能声称“简单且有效”。

S1 · SQLite 的提交与部署边界

SQLite：Write-Ahead Logging；PRAGMA synchronous。WAL 需要同宿主共享协调；FULL 与 NORMAL 的掉电耐久不同。本书的每 Work 本地账本及 FULL 是设计选择。

S2 · WAL-reset 修复要求

SQLite：WAL-reset bug。官方记载 2026 年发现的竞态及修复/回移版本；本书据此要求实际引擎包含修复，而不是把较新的驱动名当证明。

S3 · Git 原始字节

Git：hash-object。原始对象写入可不经过属性过滤。Loom 仍须自己确定授权捕获范围和必要元数据。

S4 · Git 持久设置

Git：core.fsync / core.fsyncMethod。组件是否加固影响异常关机时的结果；本书采用 all/fsync，配合对象保留及提交顺序。

S5 · 目录项耐久

Linux man-pages：fsync(2)。文件同步与目录项同步分别处理；底层存储是否遵守语义仍需验证。

S6 · 成熟进程隔离设施

systemd：执行环境官方手册源；systemd：进程清理官方手册源。用来核对受控启动、文件视图及进程组管理的实现边界，不声称仅使用 systemd 就达到完整隔离。

S7 · Pi 的可用集成边界

Pi 官方仓库；agent-core 文档；模型 API 文档。文档给出模型调用、工具钩子与原生状态接口；观察型事件流不自动成为耐久屏障。具体 API、包名、继续格式和 hook 行为以锁定版本验证，不把移动分支当发布依赖。

S8 · OpenSandbox 的官方 SDK 与 API

OpenSandbox 官方仓库；Go SDK 文档。官方提供 Go SDK 与生命周期/执行接口；Loom 在适配层增加自己的责任绑定，不复制其平台。

S9 · JSON-RPC 不负责业务幂等

JSON-RPC 2.0 Specification。id 关联响应，notification 不提供确认；Loom 的持久请求身份、授权、消息分帧和版本协商是本书补充的协议约束。

S10 · 配置语法

TOML 1.0.0。TOML 只规定语法；`work.toml` 字段与业务语义由本书定义。

S11 · 数据库导出

SQLite Backup API；SQLite WAL 文件说明。数据库一致快照不自动形成 Work 跨文件原子导出；还需协调内容、责任和引用。

S12 · DSH / Cordis 的借鉴边界

借鉴 DSH 的能力边界、接口发现与行为验证；Loom 采用持久交接后的整体重新加载，不将 Cordis 的动态组合与可撤销实现纪律作为 Harness 的接入前提。

采用预算可见、正文可转引用、当前理解可维护与原文可查询的组合，主动控制作为参考默认而非效果定论；代码任务的观察折叠实验不能替代长期助手的更正、时间与召回测试。依据：Claude 窗口与预算说明、The Complexity Trap、LongMemEval与上下文工程实践；这些来源不证明 Loom 已有效。
