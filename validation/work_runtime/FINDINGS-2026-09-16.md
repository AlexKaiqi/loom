### 反例 002 → 契约修订：`final` 只是提案，轮结束由 harness 决定

根因：runtime 原来把 `final` 硬编码为"轮结束"。模型于是可以只改文件、不发声明，状态变化不进事实流——正是设计禁止的 **E5 内容当侧信道**。
修复：
1. runtime 不再因 `final` 直接结束；改为调用 `rounds.should_continue(state)`，harness 说停才停，并把被驳回的 final 文本通过 `rejected_final` 回传给下一次投影。
2. goal / plan 的 `should_continue` 把 final 视为合法结束；**archive 的 `should_continue` 只认 `archive.performed`**——没有声明就不许结束。
3. archive 投影在被驳回后明确提示"上一次 final 未被接受，必须声明折叠"。

结果：003 在第 4 步补发了 `archive.performed`，从"文件系统改了就完事"变成"改动必须落到事实"。这条比前两个反例更接近设计核心（E2/E5）。

## 追加（同一日）：崩溃残留与恢复（head 是提交点）

目标：Round 中途失败后，**不能靠重跑掩盖**——未提交的事实尾部必须可识别、隔离、留痕。

首次实现被自己的用例推翻：原本用 `head.facts_end` 判断"未提交尾部"，但**外部受理的事实本来就落在提交水位之后**（合法的待处理输入），会被误判成崩溃残留——`offline_crash_recovery` 第一次 9/11 FAIL 暴露了它。

修复（改用显式轮标记，符合"按原身份核对"）：
1. `ledger/rounds.jsonl` 增加 `phase: start | commit | abort` 行；轮记录只数 `commit`。
2. `run_round` 入口若最后一行是 `start`（无后续 commit）→ 返回 `recovery_needed`（带 `round_id`、`last_committed_seq`），**不再继续/重跑**。
3. 新增 `lore_task recover`：把尾部事实原字节存入 `session/crashed/`（观测区），把 `surface/facts.jsonl` 原子截断到该轮的 `trigger_seq`，写 `ledger/repairs.jsonl`，并在 rounds 里补一条 `abort`。
4. 离线用例 `offline_crash_recovery.py` **11/11 PASS**：崩溃抛出、拒绝续跑、隔离保原文、截断、repair 留痕、恢复后正常提交、且崩溃前已落盘的 content 改动**仍在**（文件效果与事实尾部要分开对待）。
5. 全部离线用例复跑：goal 9 + plan 11 + archive 14 + ask-user 13 + crash 11 = **58 PASS**；真实 goal/plan 的独立校验器在新 ledger 格式下复跑仍全绿。

已知边界：崩溃点如果发生在 `start` 标记写入之前（受理后、轮未开始）不算崩溃；发生在 `commit` 写入之后、head 推进之前，目前由 `head.facts_end` 与 commit 记录不一致暴露，**尚无自动核对**——列入后续加固。

**新发现的缺口（evidence_refs 质量）**：模型的 `monitor.condition.met.evidence_refs` 是一句**描述字符串**（"tool_result: … exit=0, output READY"），不是可解析引用。契约只要求"字符串数组"，运行时不校验可解析性——证据链因此弱化。列入后续：`evidence_refs` 应限定为**路径或事实 id** 并校验存在性。离线断言全量：**82 PASS / 0 FAIL**（7 个用例）。






## 两个反例的根因与修复（都由 harness 承担，不是 runtime 特判）

1. **001 无进展循环**：投影只列"近期事实"，没有步预算、没有"已跑过的脚本不许再跑"、没有"验收已满足就必须声明完成"的规则 → 模型反复自检。
   修复（`lore_harness/goal/projection/main.py`）：投影加入剩余步数、本轮已运行脚本清单、上一条工具结果的 exit/stdout，以及三条硬规则（最多一次验收命令；满足即必须 emit；剩余 0 必须给决定）。
2. **002 重复完成**：轮的结束条件原本落在 runtime 的 `max_steps`，hooks 不参与 → 模型每步都发 `task.completed`。
   修复：runtime 新增 `rounds.should_continue(state)` 调用点（**轮结束条件归 harness**，对齐"Round 的结束由 rounds 逻辑决定"）；goal harness 在完成声明后返回 False，循环立即停止。

附带发现并修复：`importlib` 会把 `__pycache__` 写进只读的 `harness/`，改变 harness digest。现在加载时禁用字节码写入，且每轮开始/结束都重算 harness digest，变了就**响亮失败**（`_assert_harness_readonly`）。

## 追加（同一日）：system-design 场景，冻结/修订/失效 + 条件声明

runtime 新增**条件声明（base_rev 比较交换）**：`emit` 可带 `base_rev`，runtime 与轮开始时记录的已提交 revision 比对，不符则落 `sys.declaration.rejected` 并拒绝该声明（不静默覆盖）。

harness `system_design`：单元定义在 `units/<id>.md`；`design.unit.accepted` 由模型声明，**冻结（`design.unit.frozen`）与文件 digest 由 harness 从真实字节派生**；`design.freeze.violation` 检出未经授权的字节改动；`design.amendment.accepted`（外部）才解冻；依赖被修订后，下游单元自动标 `design.unit.stale`；全部单元冻结且无违规才派生 `task.completed`。

离线用例 `offline_system_design.py` **18/18 PASS**，覆盖完整生命周期：冻结 → 陈旧基线被拒 → 越权改动检出且阻止完成 → 修订重冻 → 依赖失效传播 → 重新接受后完成。

**真实运行 `ark-design-002` 是本次最有价值的反例（三条叠加）**：
1. 目标给了两个单元，模型**连续 4 步反复重写 u1.md**，从不声明接受——正是"不局部改、来回调整"的病；
2. **写错路径**：投影原写"content/units/…"，而 cwd 已是 content，文件落到 `content/content/units/`——提示与工作目录语义不一致；
3. 每步 reasoning 11k–32k token，`--max-tokens 16000` 下极慢，整轮被外层超时杀掉。

根因与修复：
- 投影改为 `units/<id>.md`（相对 content，明确不要加 `content/` 前缀），并加"本轮已运行脚本"清单与"同一文件每轮最多写一次，写过就必须接受"的规则；
- `should_continue` 改为**无进展不许收轮**（裸 final / 空回复不算结束）——与 archive 同一条教训；
- 超时/预算按 ark 修订的 reasoning 现实重新给（单轮 max_tokens 8000、调用超时 280s）。

**这次真实中断同时验证了崩溃机制**：任务停在 `phase=start` 且已有 2 条未提交事实；`lore_task recover` 把尾部原字节存入 `session/crashed/`、截断到该轮的 `trigger_seq`（objective）、写 `ledger/repairs.jsonl`（见 `evidence/ark-design-002/04-recover.json`）。

**`ark-design-004` 暴露第二层病**：路径修对后，模型仍在同一轮里**连写 4 次 `u1.md`（每次文本略不同）却从不声明接受**——"重复脚本"这类字面守卫抓不到。
修复：runtime 新增 **`logic.guard(state, action)`** 钩子——harness 可在动作执行前拒绝它；被拒绝即落 `sys.action.rejected` 事实并继续本轮（要求 manifest 声明该 kind）。system_design 的 guard 规则：本轮的当前单元文件已写过一次 → 拒绝再写，理由是"必须改为声明接受"。这是把"不许原地打转"从提示词变成机制。

**`ark-design-005` 成功（真实模型）**：
| 轮 | 步骤 | 事实 |
|---|---|---|
| R1 | 5 | objective → tool → `design.unit.accepted(u1)` → **`design.unit.frozen(u1)`**（harness 从字节算 digest） |
| R2 | 3 | tool → `accepted(u2)` → `frozen(u2)` → **`task.completed`**（派生） |

独立校验 `verify_design_task.py` **14/14**：每个冻结单元的 digest 与真实文件字节复算一致、依赖顺序 u1→u2、无违规/失效/被拒声明、完成仅出现一次且在末条、head 与末条事实一致、每单元恰好一轮、无未提交残轮。离线 `offline_system_design.py` **18/18**。


## 追加（同一日）：delegation 场景，跨任务授权（wants + grants）

runtime 新增：`relate`（在 `task.json.relations` 声明 `wants`/`grants`，按稳定 task id）与 `deliver`（把一条事件投递到另一个任务的门）。**只有接收方 wants 且发送方 grants 才放行**；不符即拒绝并记在接收方的受理账上，没有隐式授权、没有回落。两个 harness：`delegation_parent`（委派一次 → 等报告 → 收尾）与 `delegation_child`（按 scope 干活 → 报回结果 → 派生完成）。

| parent R2 | 收尾 | `task.completed`（1 步） |

独立校验 `verify_delegation_tasks.py` **16/16**：两侧事实顺序、子任务交付物真实存在且内容正确、父任务 content 为空（**父从不碰子任务内容**）、四个关系声明齐备、两条受理记录的来源正确、两侧 head 与末条事实一致。离线 `offline_delegation.py` **14/14**，含**未授权投递被拒并留痕**。

**第一次真实运行（`ark-delegation-001`）暴露投影歧义**：父任务投影里一句裸的 `completed: False`（指父任务）被模型读成"子任务报告未确认"，于是它**正确地拒绝**发明完成声明，只回 final。修复：投影明确写 `parent task completed`，并规定"存在 `task.reported` 就是确认，下一步必须 emit 完成"；父 harness 的 `should_continue` 改为**无进展不许收轮**（与 archive/system-design 同一教训）。另修 CLI 顺序 bug：`deliver` 没有 `--root`，原实现会先算 base 而崩溃。

## 追加（同一日）：research 场景，确定性召回 + 来源摘要校验

runtime 新增 **`recall` 动作**：对任务自身 content 做**字面、大小写不敏感、有界**的检索，结果作为 `sys.recall.result` 观测事实（**不是模型调用、不是 embedding**；模型辅助召回仍未实现）。回放恢复的是已记录事实，不重跑检索。harness `research` 用"声明 source → 记录 finding → 声明饱和"推进，`task.completed` 由 settle 在饱和且来源全部有效时派生。

真实运行 `ark-research-001/002/003` 暴露**三类真实病**（全部保留）：
1. **路径歧义**（同 system-design）：模型反复 `cd <绝对 content 路径>` 原地探索；投影改为"shell cwd 就是这里，用相对路径，不要 cd"。
2. **探索不收敛**：模型连续多轮只 grep/cat、从不声明。加 `logic.guard`：本轮已有 2 次 shell 读取且没有任何声明 → 拒绝继续探索（`sys.action.rejected`），逼它声明。003 第 3 轮才终于落下 `source.added` + `finding.recorded`。
3. **编造摘要（本轮最重要的发现）**：模型注册来源时给了一个**凭空写的 sha256**，而 harness 只检查字段存在——正是"应用声明当证据"的反面教材。
